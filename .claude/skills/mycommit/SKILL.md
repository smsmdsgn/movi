## タスク

上記の変更内容を検証し、コミットを作成する。
補足指示があれば考慮する: $ARGUMENTS

### 手順1: 禁止ファイルの確認

以下が変更対象に含まれていないか確認する。
**1件でも含まれていれば、コミットせずに報告して中断する。**

- `.env`（`.env.example` は対象外）
- `.htpasswd`
- 秘密鍵・証明書（`*.pem` `*.key` `id_rsa` など）
- `storage/app/public/` 配下のアップロード画像
- `node_modules/` `vendor/`

差分の中に、以下の文字列が含まれていないかも確認する。

- `sk_live_` `sk_test_` `pk_live_` で始まる文字列
- `password` `secret` `api_key` に続く具体的な値
- Basic認証の認証情報

### 手順2: 実装の残骸の確認

差分に以下が含まれていないか確認する。
含まれていれば一覧で報告し、**コミットしてよいか確認を求める。**

- `dd()` `dump()` `var_dump()` `ray()`
- `console.log` `debugger`
- コメントアウトされたコードブロック
- 新規に追加された `TODO` `FIXME`
- `.only` `.skip` が付いたテスト

`docs/design.md` の変更が含まれる場合、版数が1つだけ上がっているか確認する。
複数上がっている場合、最終状態に対する1つに直す。

### 手順3: コミットの分割判断

変更が**複数の目的**にまたがっていないか判断する。
以下は別コミットに分ける。

- 機能の実装と、無関係なリファクタリング
- 機能の実装と、コード整形のみの変更
- 複数の機能をまたぐ変更
- マイグレーションの追加と、それに無関係な画面修正

分割が必要と判断した場合、**分割案を提示して確認を求める。**
承認されたら、ファイル単位で `git add` を分けて複数回コミットする。

### 手順4: コミットメッセージの作成

```
{type}: {変更内容の要約}

{変更の理由。1〜3行}

{補足があれば箇条書き}
```

| type | 用途 |
|---|---|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `refactor` | 挙動を変えない内部構造の変更 |
| `style` | 整形のみ（Pint の適用など） |
| `test` | テストの追加・修正 |
| `docs` | ドキュメントの変更 |
| `chore` | 設定・依存パッケージ・ビルド関連 |

**要約の書き方**

- 日本語で記述する
- 50文字以内に収める
- 「修正」「対応」のような、何をしたか判別できない表現を使わない

**本文の書き方**

本文は「何のために」「何を」「どう変更したか」の3点が読み取れるように書く。
目的と実装内容の両方を残し、後から読み返して判断の経緯と手法の双方を辿れる状態にする。

| # | 要素 | 内容 |
|---|---|---|
| 1 | 目的 | 解決しようとした問題、または実現しようとした状態 |
| 2 | 対象 | どの層・どのクラス・どのテーブルに手を入れたか |
| 3 | 手法 | どのような方法で実現したか。採用した仕組みや構文を具体的に書く |

- 3について、既知の手法を使った場合はその名称を明記する
  （生成列、グローバルスコープ、楽観的ロック、モデルイベント など）
- 通常とは異なる方法を採った場合、その方法を選んだ理由も添える
- 設計上の判断を伴う場合、基本設計書の該当章を参照する（例: `docs/design.md 6.4.2 参照`）
- 自明な変更（整形、誤字修正）では本文を省略してよい

**例**

```
feat: 座席ロックの取得と延長を実装

複数の利用者が同一座席を同時に選択できる状態を解消するため、
座席の一時確保を実装した。

- t_seat_locks に (screening_id, seat_id) のユニーク制約を張り、
  排他をDB側で担保する。アプリケーション側の存在チェックでは
  わずかな時間差で複数の取得が成立しうるため
- 取得・延長・解放を SeatLockService に集約し、
  テーブルへの直接操作を各所に書かない
- 有効期限は10分。決済画面への遷移時に15分へ延長する
- docs/design.md 6.4 参照
```

```
fix: キャンセル済み座席が再販できない問題を修正

予約データを削除しない方針のため、キャンセル済みの行が
ユニーク制約に残り、同一座席を再度販売できなくなっていた。

- t_reservation_seats に released_at を追加し、
  active_seat_id を生成列とした
  （released_at IS NULL のとき seat_id、それ以外は NULL）
- ユニーク制約を (screening_id, active_seat_id) に張り替えた。
  MariaDB のユニークインデックスが NULL の重複を許容する性質を利用している
- 親の status 変更と released_at の更新は同一トランザクションで行う
- docs/design.md 6.4.2 参照
```

```
refactor: 管理画面の館スコープをグローバルスコープに集約

各画面に絞り込み条件を記述しており、追加時の書き漏れによって
他館のデータが参照できる状態が生じうるため。

- CinemaScope を作成し、対象モデルに適用した
- cinema-admin でログインしている場合のみ cinema_id の条件が付加される
- 各コントローラおよび Livewire コンポーネントから
  where('cinema_id', ...) の記述を削除した
- docs/design.md 4.8.1 参照
```

### 手順5: 実行

作成したメッセージを提示し、**承認を得てからコミットする。**
`git push` は実行しない。

### 禁止事項

- コミットメッセージに Claude や AI に関する記載を含めない
- `git commit --no-verify` を使用しない
- `git add .` で無条件に全ファイルをステージしない。変更内容を確認して選択する
