## 1. はじめに

### 1.1 本書の目的

架空のシネマコンプレックスチェーン「ムビ」の公式サイトについて、
機能要件・非機能要件・システム要件およびデータベース設計を定義する。

### 1.2 適用範囲

本書は顧客向けサイトおよび管理サイトの双方を対象とする。

**実施する事項**

| # | 事項 | 備考 |
|---|---|---|
| 1 | 顧客向けサイトの実装 | 上映情報、予約、決済、マイページ、お知らせ、静的ページ |
| 2 | 管理サイトの実装 | マスタ管理、上映編成、上映回、予約状況、入場確認、バナー、お知らせ |
| 3 | **メール送信** | Brevo 経由で実際に送信する。予約確定・キャンセル・無料鑑賞券・パスワードリセット |
| 4 | 決済 | Stripe のテストモードで実装する。実課金は行わない |
| 5 | 入場ゲート画面 | Webアプリケーションとして実装する。カメラでQRコードを読み取る |
| 6 | 画像アップロード | バナー画像のみ |
| 7 | 初期データの生成 | 過去2年分の上映実績および予約データ |
| 8 | エックスサーバーへのデプロイ | 手動デプロイ |

### 1.3 記述上の規約

- 設計判断の根拠を要する箇所には **【根拠】** を付す
- 未確定事項には **★** を付し、12章に一覧を記載する

### 1.4 本書の運用（Claude Code）

本書はリポジトリの `docs/design.md` に配置し、`CLAUDE.md` から参照する。

## 2. システム概要

### 2.1 システムの位置づけ

映画館チェーンの公式サイトとして、上映情報の提供、座席指定予約、決済、
入場管理、会員向け特典管理、コンテンツ配信を行う。

チェーン名は「ムビ」。旗艦店の祇園ムビのみ命名規則が異なり、他館は「ムビ○○」形式とする。
館数および出店エリアは仕様として固定せず、館はマスタデータとして増減可能とする。

### 2.2 利用者区分

| 区分 | 認証 | 主な操作 |
|---|---|---|
| 非会員 | なし | 上映情報閲覧、氏名・フリガナ・電話番号・メールアドレスの入力による予約・決済 |
| 会員 | メールアドレス | 上記に加え、予約履歴参照、スタンプカード、無料鑑賞券の使用 |
| `cinema-admin` | 発行ID | 自館の上映回登録、予約状況確認、お知らせ投稿、入場確認 |
| `super-admin` | 発行ID | 全館のマスタ管理、上映編成、バナー管理、管理者アカウント管理 |

### 2.3 主要機能一覧

| # | 機能 | 概要 | 章 |
|---|---|---|---|
| F-01 | 系列館切替 | URL単位で館を切り替え、以降の表示を当該館にスコープする | 4.1 |
| F-02 | 上映情報閲覧 | 上映スケジュール表、作品一覧、作品詳細 | 4.2 |
| F-03 | 座席指定予約 | 座席ロックを伴う座席選択、券種選択、決済 | 4.3 |
| F-04 | 予約キャンセル | 上映20分前までの取消および返金 | 4.4 |
| F-05 | 会員特典 | スタンプカード、無料鑑賞券 | 4.5 |
| F-06 | 入場管理 | QRコード発行および入場確認 | 4.6 |
| F-07 | コンテンツ管理 | お知らせ、バナー | 4.7 |
| F-08 | マスタ管理 | 館、映画、シアター、券種、上映規格、上映編成 | 4.8 |
| F-09 | 静的コンテンツ | 料金表、アクセス、施設案内ほか | 4.9 |

### 2.4 完成条件

以下をすべて満たした時点で完成とする。

**顧客側**

1. 館を切り替えて上映スケジュールを閲覧できる
2. 会員登録せずに座席を選び、決済し、予約を完了できる
3. 会員がマイページで予約履歴とスタンプ数を参照できる
4. 会員・非会員のいずれも上映前に予約をキャンセルできる
5. 予約確定メールに入場用QRコードが届く

**管理側**

6. `super-admin` が館・映画・料金・上映編成・バナーを登録でき、全館の予約状況を確認できる
7. `cinema-admin` が自館の上映回を登録し、予約状況確認・お知らせ投稿・入場確認を行える
8. `cinema-admin` が他館のデータに一切アクセスできない
9. QRコードによる入場処理が行える

**共通**

10. PC・タブレット・スマートフォンの実機で表示および操作が破綻しない

### 2.5 適用範囲外

#### 2.5.1 機能・構成

| 項目 | 理由 |
|---|---|
| 本番決済 | テストモードのみで動作させる |
| **お問い合わせの実メール送信** | フォームはダミー実装とし、送信完了画面にその旨を明示する（4.9.2） |
| 予約内容の変更（日時・座席の振替） | キャンセル後の再購入で代替する |
| 劇場精算（座席のみの取り置き） | 決済経路が2系統となり、予約確定・キャンセル・返金・無料鑑賞券の消費・空席計算・入場コード発行の各処理に分岐が波及するため。現金購入は劇場窓口での当日券販売で対応する |
| 会員の退会機能 | 予約データを分析対象として保持するため。退会を希望する利用者へは、マイページに「退会をご希望の場合は劇場窓口までご連絡ください」の案内文を表示する（お問い合わせフォームはダミー実装のため案内先に含めない。P-05 マイページ、7.14 構成要素5 で対応） |
| 多言語対応 | |

| SMS通知 | Brevo の有料機能であり、無料プランの範囲を超える |
| 二要素認証 | 17.14 参照 |
| 常駐プロセスを要する構成（キューワーカー、WebSocketサーバー） | 共有レンタルサーバーでは Supervisor が使用できない。Cron と `wire:poll` で代替する（3.4 / 6.4.3） |

## 3. システム要件

### 3.1 動作環境の前提条件

アプリケーションの動作に必要な条件を以下に示す。
本番環境はエックスサーバー スタンダードプランを使用するが、
アプリケーションは以下の条件を満たす環境であれば動作するものとする。

| 区分 | 必要条件 | 契約プランの提供状況 |
|---|---|---|
| PHP | 8.3 以上（8.4 を使用） | 8.5 / 8.4 / 8.3 ほか |
| PHP拡張 | PDO / mbstring / openssl / **GD** / fileinfo / bcmath | 標準で利用可 |
| データベース | MariaDB 10.3 以上、または MySQL 5.7 以上（**MariaDB 10.11** を使用） | MariaDB 10.11.x |
| Webサーバー | Apache または Nginx。ドキュメントルートを任意のディレクトリに向けられること | Apache 2.4 |
| ジョブ実行 | 1分間隔でコマンドを実行できるスケジューラ（Cron） | 利用可 |
| 外部通信 | サーバーから HTTPS の外部接続ができること（Stripe / TMDB / Turnstile の検証） | 利用可 |
| メール送信 | 外部 SMTP サーバーへ接続できること（Brevo） | 利用可 |
| ファイル保存 | アプリケーションから書き込み可能な永続ディレクトリ | 利用可 |
| Composer | 実行できること | 手動導入が必要（15.3） |

**GD拡張について**

QRコードのPNG生成に使用する。Imagick は共有レンタルサーバーで
利用できない場合があるため、GD で動作するライブラリを選定する（4.6.2）。

| 区分 | 採用 |
|---|---|
| フレームワーク | Laravel 13 |
| 認証基盤 | Laravel 13 公式スターターキット（Livewire版） |
| フロントエンド | Livewire 4 / Alpine.js / Tailwind CSS |

### 3.3 バージョン選定

#### 3.3.1 PHP 8.4

**【根拠】** Laravel 13 は PHP 8.3〜8.5 に対応するが、次の理由により 8.4 を採用する。

1. Laravel 13 が内包する Symfony 8 コンポーネントの動作実績が 8.4 に集中している
2. Composerパッケージには対応PHPの上限を宣言するものがあり
   （例: `"php": "^8.1|^8.2|^8.3|^8.4"`）、8.5 では依存解決に失敗する可能性がある

8.5 へ変更する場合は、Stripe SDK・QRコード生成・Turnstile関連の各パッケージが
8.5 で解決することを確認したうえで切り替える。

#### 3.3.2 MariaDB 10.11

**【根拠】** MySQL 5.7 はウィンドウ関数およびCTEを持たない。
上映回別の残席集計で使用可能な手段が制限されるため MariaDB を採用する。
10.11 は開発元が LTS として提供する版である。

Laravel 11 以降は MariaDB 専用ドライバを備えるため、`DB_CONNECTION=mariadb` を指定する。

**ローカル開発環境**

| 項目 | 採用 |
|---|---|
| PHP / Web サーバー | Laravel Herd（Windows / macOS 共通） |
| データベース | MariaDB 10.11（Docker） |

**【根拠】** XAMPP・MAMP は同梱する PHP が 8.2 までであり要件を満たさない。
Herd は Windows と macOS の双方に対応し、PHP 8.4 を含む複数バージョンを切り替えられる。

データベースをコンテナで実行するのは、
2つの開発環境でバージョンと設定を一致させるためである。

### 3.3.3 認証基盤

Breeze / Jetstream は Laravel 12 以降で非推奨となり、公式が追加更新を行わない旨を明示している。
Livewire版スターターキットを採用する。
Laravel 13 の Livewire スターターキットは Livewire 4 / Tailwind / Flux UI で構成される。

**スターターキットはプロジェクト作成時にのみ選択できる。**
`laravel new {name} --livewire` で作成する。
`composer create-project laravel/laravel` では素のスケルトンが生成され、
後から追加することはできない。

同梱の Flux UI は認証画面および管理画面に限定して使用し、顧客向け画面は素の Tailwind で構築する。

### 3.4 アプリケーション設計に影響する実行環境の条件

以下は、アプリケーションの実装方針を決定づける条件である。

| # | 条件 | 実装への影響 |
|---|---|---|
| C-01 | **常駐プロセスを起動できない**（Supervisor が使用できない） | キューワーカーを常駐させない。非同期処理が必要な場合はスケジューラ経由で実行する |
| C-02 | **WebSocket サーバーを運用できない**（C-01 に起因） | 座席状況の反映はポーリングで行う（6.4.3） |
| C-03 | 1分間隔のスケジューラを利用できる | 座席ロックの解放、予約の期限切れ処理、スタンプ付与をバッチで実装する（10章） |
| C-04 | サーバー上で Node.js を安定して実行できない | アセットのビルドを開発機で行い、成果物を配置する。**サーバー上でのビルドを前提としない** |
| C-05 | オブジェクトストレージを利用しない | アップロードファイルはローカルディスクに保存する。保存先の抽象化には Laravel のファイルシステムを使用し、ドライバの差し替えが可能な実装とする |
| C-06 | Imagick が利用できない可能性がある | 画像処理は GD で動作するライブラリを選定する |

上記以外のホスティング固有の事項（ディレクトリ構成、PHPバイナリのパス、
Composer の導入手順など）は、アプリケーションの設計に影響しないため
デプロイ手順（15.3）に記載する。

### 3.5 環境非依存の方針

アプリケーションは特定のホスティング環境に依存しない実装とする。

| # | 方針 |
|---|---|
| 1 | 環境ごとに異なる値は `.env` および `config/` で吸収し、コードに直接記述しない |
| 2 | ファイルパスは `storage_path()` / `public_path()` 等のヘルパを使用し、絶対パスを記述しない |
| 3 | ファイル保存は Laravel のファイルシステム経由で行い、`file_put_contents()` 等で直接書き込まない |
| 4 | データベースへのアクセスは Eloquent およびクエリビルダを使用し、MariaDB 固有の構文に依存しない。ただし生成列（6.4.2）は例外とし、使用箇所をマイグレーションに限定する |
| 5 | 外部サービスの接続情報は `config/services.php` に集約する |

**【根拠】** ホスティング環境の変更や、ローカル環境との差異によって
アプリケーションの修正が必要になる状態を避ける。

本館と商業館という性格の違いにより上映作品と規格構成を分ける。

館トップページおよび施設案内ページに表示する。

#### 4.1.2 URL設計

館を URL パスに含める。キーは `m_cinemas.slug`。

```
/cinemas/{slug}                 館トップ
/cinemas/{slug}/schedule        上映スケジュール
/cinemas/{slug}/movies/{id}     作品詳細
/cinemas/{slug}/access          アクセス
/cinemas/{slug}/establishment   施設案内
/cinemas/{slug}/news            お知らせ
```

**【根拠】** セッションのみで館を保持する場合、館別ページのURLが一意にならず、
共有および検索エンジンによるインデックスができない。

館に依存しないページ（会社情報、採用情報、料金表）は `/{page}` 直下に配置する。

#### 4.1.3 動作仕様

| # | 項目 | 仕様 |
|---|---|---|
| 1 | 館の保持 | セッションおよびCookieに保持し、再訪時に復元する |
| 2 | 初期値 | 未選択時は祇園ムビとする |
| 3 | スコープ範囲 | 上映スケジュール、上映作品、シアター、座席、予約、お知らせ |
| 4 | 切替時の遷移先 | 現在のページと同種のページへ遷移する |
| 5 | 館の解決 | ルートグループのミドルウェアで `{slug}` から解決し、リクエスト全体で共有する |
| 6 | slugの形式 | 半角英小文字とハイフンのみ（例: `gion`, `shijo-karasuma`）。先頭・末尾のハイフンと連続したハイフンは認めない。館マスタで一意。正規表現は `[a-z]+(?:-[a-z]+)*` とし、ルート制約（4.1.3 追記表）と A-03 のバリデーション（4.8.2）で同一のものを用いる |

**実装で確定した事項**

| 対象 | 内容 | 理由 |
|---|---|---|

### 4.3 F-03 座席指定予約

#### 4.3.1 予約フロー

```
上映回選択
  → 座席選択（ロック取得）
  → 同意画面（予約内容の確認と利用規約への同意）
  → 会員 / 非会員の選択
       ├─ 会員   : ログイン
       └─ 非会員 : お客様情報の入力
  → 券種選択
  → 決済
  → 予約確認
  → 予約完了（QR表示・メール送信）
```

**販売期間**: 上映日の3日前 0:00 から、上映開始時刻まで。

**ログインを求めるタイミング**

座席選択の時点では認証を求めない。座席を選んでから会員／非会員を選択する。
座席ロックは**セッションIDを保持者として取得し、ログイン後にユーザーIDへ引き継ぐ**。

**【根拠】** 座席を見る前にログインを求める構成は、
一般的なシネマコンプレックスの予約導線と異なり、離脱要因となる。

#### 4.3.2 会員と非会員の差異

| 項目 | 会員 | 非会員 |
|---|---|---|
| 入力 | ログインのみ | 氏名 / フリガナ / 電話番号 / メールアドレス |
| スタンプの付与 | あり | なし |
| 無料鑑賞券の使用 | 可 | 不可 |
| 予約履歴の閲覧 | マイページ | 予約照会画面（4.3.5） |
| ロックの保持者 | ユーザーID | セッションID |
| データの保持 | 保持 | 保持 |

`t_reservations.user_id` は NULL 許容とし、非会員の予約では入力値を直接保持する。
非会員が後から会員登録した場合も過去の予約は紐づけない。

**【根拠】** メールアドレスの本人性を検証していないため、
紐づけを許すと他人の予約を取り込める。

#### 4.3.3 予約ステータス

| ステータス | 意味 | 遷移先 |
|---|---|---|
| `pending` | 座席選択中・決済未完了 | `paid` / `expired` |
| `paid` | 決済完了 | `cancelled` |
| `expired` | 座席ロックの期限切れによる無効化 | 終端 |
| `cancelled` | 顧客によるキャンセル | 終端 |

| 状態 | 座席の占有 | 入場コードの発行 | スタンプ付与 |
|---|---|---|---|
| `pending` | 座席ロックのみ | なし | なし |
| `paid` | 予約座席として確定 | あり | あり |
| `expired` / `cancelled` | 解放 | — | なし |

`expired` への遷移はバッチ処理による（10章）。

ステータスは `App\Enums\ReservationStatus` として定義する。
将来的に決済を伴わない座席確保（取り置き）を追加する場合、
本 enum への値の追加で対応できる構造とする。

#### 4.3.4 制限事項

| 項目 | 値 |
|---|---|
| 1予約あたりの座席数 | 最大8席 |
| 1利用者が同時に保持できるロック | 1上映回・8席まで |

別の上映回の座席選択に移行した時点で、前の上映回のロックを解放する。

**【根拠】** 制限がない場合、単一の利用者が多数の座席を占有した状態で放置できる。

上限を8席とするのは、三世代での来場（大人4名・子供4名など）を
1回の予約で完結させるためである。
国内シネコンでは6枚前後を上限とする例が多いが、
本システムでは家族単位の来場を分割させない方針を採る。

#### 4.3.5 予約照会画面

会員・非会員を問わず利用できる予約照会画面を設ける。

**URL**: `/lookup`

| 方式 | 入力項目 | 用途 |
|---|---|---|
| A（標準） | 予約番号 ＋ メールアドレス | 通常の照会 |
| B（予約番号の紛失時） | メールアドレス ＋ 電話番号 ＋ 上映日 | 控えを失った場合の復旧 |

| 項目 | 仕様 |
|---|---|
| 表示内容 | 予約内容、入場用QRコード、予約番号、領収書 |
| 実行可能な操作 | キャンセル |
| 複数件が該当する場合 | 一覧表示し、選択させる |

予約確定メールに記載するURLは、本画面へ予約番号を事前入力した状態で遷移させる。

**【根拠】** 方式Bは認証要素が方式Aより弱いが、
メールアドレス・電話番号・上映日の3項目を同時に知り得る第三者は限定される。
控えを失った利用者が予約に到達できない状態を避けることを優先する。

**予約番号**

| 項目 | 仕様 |
|---|---|
| 形式 | 8桁の数字 |
| 表示形式 | 4桁ずつハイフンで区切る（例: `1234-5678`） |
| 入力 | ハイフンの有無を問わず受け付ける |
| 付与対象 | 会員・非会員を問わず全予約 |
| 用途 | 予約照会、入場時の手入力、問い合わせ時の識別 |

**【根拠】** 入場コードは32文字のランダム文字列であり、口頭伝達や手書きに適さない。
照会用の短い識別子を別に設ける。

#### 4.3.6 非会員の入力項目

| 項目 | 仕様 |
|---|---|
| 氏名 | 全角文字 |
| フリガナ | **全角カタカナのみ** |
| 電話番号 | ハイフンなしの半角数字 |
| メールアドレス | **必須**。予約確定メールの送信先および本人照合に使用する |

**【根拠】** メールアドレスを必須とすることで、
予約の控えとQRコードを確実に届けられる。
メールアドレスを保有しない利用者は、劇場窓口での当日券購入を案内する。

#### 4.3.7 同意画面

券種選択の前に、予約内容の確認と利用規約への同意を求める。

| # | 表示項目 |
|---|---|
| 1 | 劇場名 |
| 2 | 作品名 |
| 3 | シアター名 |
| 4 | 上映日時 |
| 5 | 選択した座席と枚数 |
| 6 | オンラインチケット購入に関する利用規約（要約と全文へのリンク） |
| 7 | 同意チェックボックス（未チェックでは次へ進めない） |

**同意を求める事項**

- 購入後の内容変更ができないこと（キャンセルのうえ再購入となる）
- キャンセル期限が上映開始の20分前であること
- 上映開始後の入場について

**【根拠】** 予約確認画面（決済直前）と表示内容が重複するが、
「規約への同意」と「決済内容の最終確認」は目的が異なる。
同意を決済直前に置くと、規約を読むために決済フローから離脱させることになる。

### 4.4 F-04 予約キャンセル

予約内容の変更機能は提供せず、キャンセル後の再購入で代替する。

| # | 項目 | 仕様 |
|---|---|---|
| 1 | 期限 | 上映開始時刻の20分前まで |
| 2 | 単位 | 予約単位。座席の一部取消は不可 |
| 3 | 手数料 | なし（全額返金） |
| 4 | 返金処理 | Stripe Refund API を使用 |
| 5 | 制限 | `checked_in_at` が設定済みの予約は不可 |

**【根拠】** 国内シネコンでは上映開始の20分前前後を期限とする例が一般的であり、
これに合わせる。

前日締切（当日0時）とした場合、当日の予定変更に対応できず、
キャンセルされないまま来場しない予約（無断キャンセル）が増える。
無断キャンセルは席が空席のまま販売されないため、直前キャンセルより損失が大きい。

座席の買い占めによる妨害行為は、キャンセル期限ではなく
1予約あたりの座席数と同時ロック数の上限（4.3.4）で抑止する。

**操作導線**

| 利用者 | 導線 |
|---|---|
| 会員 | マイページの予約詳細から実行 |
| 非会員 | 予約照会画面（4.3.5）で照合したうえで実行 |

**キャンセル時の処理**

1. `status` を `cancelled` に更新し、`cancelled_at` を設定する
2. 座席を再販可能な状態に戻す（6.4.2）
3. 無料鑑賞券を使用していた場合は再利用可能に戻す（`t_reservations.active_free_ticket_id`
   は `status` の変更により生成列として自動的に解除される。6.1.2「無料鑑賞券の使用状態の
   管理方式」参照。フェーズ5までは `t_free_tickets.used_at` を `null` に戻す現行方式も残る）
4. Stripe で返金処理を行う

スタンプは上映開始時に付与するため（4.5.1）、キャンセル時点では未付与であり取消処理を要さない。

### 4.5 F-05 会員特典

#### 4.5.1 スタンプカード

| 1 | 付与単位 | 鑑賞1回につき1個 |
| 2 | 交換条件 | 5個で無料鑑賞券1枚を発行し、スタンプ数を0にリセット |

| 5 | 付与タイミング | 決済済み予約に紐づく上映回の開始時点 |

**【根拠】** 入場実績の追跡は行わないため来場の有無は問わない。
また当日の急用による不来場を考慮し、上映開始をもって1回とみなす。

**実装方針**

- バッチ処理により、開始時刻を経過した上映回のうち決済済みかつ未付与の予約を抽出して付与する
- `t_stamps.reservation_id` にユニーク制約を設定し、多重実行時の二重付与を防止する
- スタンプ数はカウンタ列を持たず、`t_stamps` の行数を集計して求める

#### 4.5.2 無料鑑賞券

| # | 項目 | 仕様 |
|---|---|---|
| 1 | 適用範囲 | 1席分の券種価格のみ |
| 2 | 追加料金 | 上映規格・座席種別の追加料金は別途支払い |
| 3 | 使用枚数 | 1予約につき1枚 |
| 4 | 有効期限 | 発行から1年 |
| 5 | 保有条件 | 会員のみ。非会員の購入では使用不可 |
| 6 | 割引との併用 | 不可 |

**適用方式**

決済画面において、保有券の一覧から選択する方式とする。コードの手入力は求めない。
コードは券の識別子としてマイページおよびメールに表示する。

**決済のスキップ条件**

支払金額が0円となる場合のみ決済フローを通さずに予約を確定する。
追加料金または同伴者分の代金が残る場合は通常の決済画面へ遷移する。

### 4.6 F-06 入場管理

#### 4.6.1 入場方式

入場は**顧客が入場ゲート端末にQRコードをかざす**方式を基本とする。
スタッフは通常操作を行わず、判定が拒否された場合のみ対応する。

| 経路 | 操作 |
|---|---|
| 通常 | 顧客がゲート端末のカメラにQRコードをかざす。判定と入場処理が自動で行われる |
| QRコードが読み取れない場合 | スタッフが手入力モードで予約番号を入力する |

#### 4.6.2 QRコード発行

| # | 項目 | 仕様 |
|---|---|---|
| 1 | 入場コード | 予約1件につき1つ。`Str::random(32)` による英数字列とし、`t_reservations.entry_code` にユニーク制約を設定する |
| 2 | QRの内容 | **入場コードの文字列のみ**。URLを含めない |
| 3 | 生成方式 | サーバー側でPNGを生成。`endroid/qr-code` のGDライタを使用 |
| 4 | 表示場所 | 予約完了画面 / 予約確定メール / マイページ予約詳細 / 予約照会画面 |

**【根拠】**

- 入場コードに連番や予約IDを使用した場合、他者のコードを推測可能となる
- QRの内容をURLとした場合、顧客が自身のスマートフォンでQRを読み取ることにより
  入場処理を実行できてしまう。コード文字列のみとし、
  読み取り側の端末が認証済みであることを前提とする
- 共有レンタルサーバーでは Imagick が利用できない可能性があるため、GDで動作する実装を選択する

メールへはPNGをCID添付として埋め込む。
あわせて予約照会画面へのリンクと予約番号を併記し、
画像がブロックされる環境でも到達可能とする。

#### 4.6.3 入場ゲート画面

**URL**: `/admin/gate`

館内に設置した端末で常時開いておくことを想定する。
管理者ガードによる認証を要し、ログイン中の管理者の所属館にスコープされる。

**動作**

| # | 処理 |
|---|---|
| 1 | カメラを起動し、QRコードの読み取りを待機する |
| 2 | 読み取り成功時、入場コードをPOSTで送信する |
| 3 | サーバー側で予約を特定して検証する（4.6.4） |
| 4 | 可の場合、`t_reservations.checked_in_at` に現在時刻を記録する |
| 5 | 判定結果を画面全体の色で表示する（可: 緑 / 不可: 赤） |
| 6 | 3秒後に自動で読み取り待機状態へ戻る |

**入場処理をGETリクエストで行わない。**

**【根拠】** GETで状態を変更する実装では、
URLの再読み込みやブラウザの先読みによって意図しない入場処理が発生する。
またCSRF対策の対象外となる。

**表示項目**

| 判定 | 表示内容 |
|---|---|
| 入場可 | 作品名 / 上映開始時刻 / シアター / 座席 / 枚数 |
| 入場不可 | 拒否理由 / 予約者名 / 上映開始時刻 |

**手入力モード**

同一画面に予約番号の入力欄を設ける。
QRコードが読み取れない場合に使用する。

**【根拠】** 通常の入場では画面の文字を読む余地がないため、
可否を色で即断できることを最優先とする。
スタッフが確認するのは拒否された場合の理由のみである。

#### 4.6.4 入場時の検証

| # | 検証 | 入場不可とする条件 |
|---|---|---|
| 1 | 館の一致 | 端末の所属館と予約の館が不一致 |
| 2 | 予約状態 | `paid` 以外 |
| 3 | 入場可能時間 | 上映開始の60分前より早い、または上映終了時刻を経過 |
| 4 | 重複入場 | `checked_in_at` が設定済み |

#### 4.6.5 入場の取消

| 項目 | 仕様 |
|---|---|
| 実行者 | `super-admin`（全館） / `cinema-admin`（自館のみ） |
| 期限 | 該当する上映回の終了時刻まで |
| 処理 | `checked_in_at` を `null` に戻す |

**【根拠】** 誤読取や重複判定の是正は入場口で即座に行う必要がある。
本部への連絡を要する運用では顧客を滞留させる。

### 4.7 F-07 コンテンツ管理

#### 4.7.1 お知らせ

**カテゴリー**

| カテゴリー | slug | 用途 |
|---|---|---|
| お知らせ | `notice` | 通常の告知 |
| キャンペーン | `campaign` | 割引・イベント・タイアップ |
| 重要なお知らせ | `important` | 休館、上映中止、システム障害 |

**対象館の保持**

単一テーブルで管理し、`cinema_id` を館のタグとして扱う。

| `cinema_id` | 表示範囲 |
|---|---|
| `null` | 全館 |
| 館ID | 該当館のみ |

抽出条件は `cinema_id IS NULL OR cinema_id = {現在の館}`。

**【根拠】** カテゴリーと対象館を同一の軸に統合した場合、
「重要なお知らせ、かつ特定館のみ」の組み合わせが表現できない。

複数館（全館ではない）への紐づけ機構は設けない。全館共通として投稿することで代替する。

**アーカイブページ**

```
/cinemas/{slug}/news                全カテゴリー一覧
/cinemas/{slug}/news/notice         お知らせ
/cinemas/{slug}/news/campaign       キャンペーン
/cinemas/{slug}/news/important      重要なお知らせ
/cinemas/{slug}/news/detail/{id}    詳細
```

**【根拠】** 通常の告知のスラッグを `news` とした場合、
URLが `/news/news` となり冗長になるため `notice` を用いる。

| 項目 | 仕様 |
|---|---|
| 1ページあたりの件数 | 25件 |
| 並び順 | `published_at` 降順 |
| 抽出範囲 | 全館共通の記事と自館の記事の両方 |

**公開制御**

`status`（draft / published）および `published_at` を保持する。
`published_at` が未来の記事は一覧・詳細ともに非表示とする。

**本文の形式**

| # | 仕様 |
|---|---|
| 1 | 本文は Markdown で保持する |
| 2 | HTMLの直接記述を許可しない。レンダリング時にHTMLタグを除去する |
| 3 | 使用できる記法は 見出し / 箇条書き / 強調 / リンク / 画像 に限定する |
| 4 | リンクには `rel="noopener noreferrer"` を付与する |

**【根拠】** 管理画面からHTMLを入力できる場合、
スクリプトの埋め込みによる攻撃が成立しうる。
`cinema-admin` は各劇場のスタッフであり、本部が全員を管理できるとは限らない。

#### 4.7.2 バナー

権限: `super-admin` のみ

**掲載位置**

| 位置 | 用途 | 想定枚数 |
|---|---|---|
| `main` | 最上部のメインバナー | 1 |
| `carousel` | カルーセルスライダー | 3〜6 |
| `sub` | 小バナー | 2 |
| `footer_link` | 下部のバナーリンク群 | 任意 |

**登録項目**: 掲載位置 / 画像 / リンクURL / altテキスト / 表示順 / 公開期間 / 対象館

| # | 仕様 |
|---|---|
| 1 | リンク先は任意のURLとし、特定のモデルには紐づけない |
| 2 | 公開期間外は非表示。期間未指定の場合は常時掲載 |
| 3 | 表示順は手動指定 |
| 4 | altテキストは必須 |

**【根拠】** リンク先をモデルに紐づけた場合、外部サイトへの誘導バナーを設定できない。

#### 4.7.3 画像アップロード方針（システム共通）

| 項目 | 仕様 |
|---|---|
| 保存先 | `storage/app/public`。`php artisan storage:link` でシンボリックリンクを作成 |
| 許可拡張子 | jpg / png / webp / avif |
| 上限サイズ | 2MB |
| リサイズ処理 | 実装しない。適切なサイズでのアップロードを運用で担保する |
| デプロイ時の注意 | `storage/` を削除・上書きしない（C-07） |

### 4.8 F-08 マスタ管理と権限

#### 4.8.1 実装方針

権限ごとに画面を分けず、同一画面を共用し、権限によりスコープと表示項目を制御する。

| # | 方針 |
|---|---|
| 1 | `cinema-admin` は自館への絞り込みが自動適用され、館の選択UIを表示しない |
| 2 | `super-admin` は画面上部に館セレクタを持ち、全館横断または特定館への絞り込みが可能 |
| 3 | 絞り込みの強制はグローバルスコープおよびポリシーで一元管理し、各画面に条件を記述しない |

**【根拠】** 画面を二重に持つと、機能追加および修正のたびに二重の作業が発生し、
片方の修正漏れによる権限逸脱を招く。

#### 4.8.2 権限分掌

境界は「マスタか、日々の運用か」に置く。

| 対象 | `super-admin` | `cinema-admin` |
|---|---|---|
| 館マスタ（名称 / slug / 住所 / 営業時間 / 施設情報） | 作成・編集 | 閲覧 |
| シアター基本情報（名称 / 番号） | 作成・編集 | 閲覧 |
| 座席の有効／無効切替 | 全館を編集 | 自館のみ編集 |
| 映画マスタ（TMDB取り込み） | 作成・編集 | 閲覧 |
| 上映編成 | 作成・編集 | 閲覧 |
| 上映回 | 全館を編集 | 自館のみ編集 |
| 券種・料金マスタ | 編集 | 閲覧 |
| 上映規格マスタ | 編集 | 閲覧 |
| バナー | 編集 | 不可 |
| 予約状況の確認 | 全館 | 自館のみ |
| 入場確認 | 全館 | 自館のみ |
| 入場の取消 | 全館 | 自館のみ |
| お知らせ | 全館共通＋任意の館 | 自館向けのみ |
| 管理者アカウント管理 | 編集 | 不可 |

**【根拠】** 館の営業時間および施設情報は更新頻度が低く、チェーン全体での表記統一が求められる。
マスタを本部に集約することで権限の判定基準が一貫し、
新規機能追加時の権限設計が一意に定まる。

上映回のみ現場に権限を残すのは、上映枠の割り当てが混雑状況および清掃工程に依存する
運用業務であるためである。座席の有効／無効切替も同様に、故障・工事等への
即時対応を要する日々の運用（6.2）であり、シアターの新設・改修（本部が判断する
マスタ変更）とは切り分けて現場に権限を残す。

`cinema-admin` が実行可能な操作は次の5つに限られる。

1. 自館の上映回の登録・編集
2. 自館の座席の有効／無効切替
3. 自館の予約状況の確認
4. 自館向けのお知らせ投稿
5. 自館の入場確認および入場の取消

#### 4.8.3 上映編成と上映回の階層

「どの作品をどの館でいつまで上映するか」と「何時からの回か」を別テーブルに分離する。

```
bookings （上映編成）
   cinema_id, movie_id, format_id, 上映開始日, 上映終了日, surcharge
        │
        └─ screenings （上映回）
              booking_id, theater_id, 開始日時, 終了日時
```

| テーブル | 登録者 | 例 |
|---|---|---|
| `t_bookings` | `super-admin` | 祇園ムビで9/1〜9/30、作品Xを MOVI GRAND 規格で上映 |
| `t_screenings` | `cinema-admin` | 9/5 10:00の回を２番シアターで |

**【根拠】** 上映期間と個別の上映時刻を同一テーブルに保持した場合、
本部と現場の権限を分離できない。分離により、上映回の登録画面では
作品・規格・期間が親から導出され、入力項目とバリデーションが簡素化される。

**上映回のバリデーション**

| # | 制約 |
|---|---|
| 1 | 親 `t_bookings` の上映期間内であること |
| 2 | 該当規格に対応したシアターであること |
| 3 | 終了時刻は「開始時刻 + 作品の上映時間 + 予告編15分」で自動計算（手動上書き可） |
| 4 | 同一シアターで前の回の終了時刻から30分以上空けること（清掃・入替時間） |

**運用前提**: `t_bookings` が存在しない館では上映回を登録できない。
初期データ投入は 館 → シアター → 映画 → 上映編成 → 上映回 の順とする。

#### 4.8.4 管理者認証

| # | 項目 | 仕様 |
|---|---|---|
| 1 | ログインID | 顧客はメールアドレス、管理者は発行された文字列ID |
| 2 | 認証ガード | 顧客と分離した `admin` ガードを使用 |
| 3 | ログインURL | `/admin/login` |
| 4 | メール起点の導線 | 招待メール・パスワードリセットリンクのいずれも実装しない |
| 5 | パスワード再設定 | `super-admin` が管理画面から直接設定 |
| 6 | 初期アカウント | `super-admin` のみシーダーで投入 |
| 7 | 削除 | 物理削除せず無効化フラグで運用 |

**【根拠】** 管理者は限定人数であり、メール経由の招待・再設定機構を要さない。
また物理削除した場合、当該管理者が登録した上映回およびお知らせとの関連が失われる。

**映画マスタ管理の要件**

- TMDB API によるタイトル検索とメタデータ取り込み
- 公開日が過去の作品のみ登録可（バリデーションで制御）

**予約状況確認の表示範囲**

**予約検索の要件**

窓口での問い合わせに対応するための機能。
予約番号、フリガナ（カタカナ）、電話番号のいずれかで予約を検索する。

| # | 仕様 |
|---|---|
| 1 | 検索結果には 予約番号 / 予約者名 / 作品 / 上映日時 / 座席 / 入場状態 を表示する |
| 2 | 該当予約の入場用QRコードを表示できる |
| 3 | メールアドレスおよび決済情報は表示しない |
| 4 | `cinema-admin` は自館の予約のみ検索できる |

窓口での照会が最終的な救済手段となる。

#### 4.8.6 実装で確定した事項

| 項目 | 内容 | 理由 |
|---|---|---|
| `admin` ガードの構成 | `config/auth.php` に `admin` guard（`session` driver）と `admins` provider（`App\Models\Admin`）を追加した。パスワードリセットの broker は追加しない | 17.1.2-5がメールを起点とする認証導線（招待・リセットリンク）を持たないと定めているため |
| ガード別リダイレクト先 | Laravel既定の `auth`/`guest` ミドルウェアはガードに関わらず `route('login')`/`route('dashboard')` へ固定でリダイレクトする。`bootstrap/app.php` で `redirectGuestsTo()`/`redirectUsersTo()` をリクエストパスに応じて分岐させ、`/admin` 配下では `admin.login`／`Admin::landingRouteName()` の解決結果（後述）へ振り分けた | 分岐しない場合、未ログインの管理者が顧客用ログイン画面へ、ログイン済みの管理者が顧客用ダッシュボードへ誤って遷移する |
| ログイン試行のレート制限の実装位置 | `throttle` ミドルウェアではなく、`App\Livewire\Admin\Auth\Login::login()` アクション内で `RateLimiter` を直接使用する | Livewireのアクションは `/livewire/update` エンドポイント経由で呼ばれ、ルートの `throttle` ミドルウェアではログインIDをキーにできないため |

### 6.2 データ保持方針

過去データは削除しない。上映実績および購買実績を分析対象として蓄積する。

| データ | 方針 |
|---|---|
| 上映編成・上映回 | 上映期間終了後も保持 |
| 予約（会員） | 保持。スタンプの根拠および鑑賞履歴として参照 |
| 予約（非会員） | 保持。非会員の購買傾向の分析対象 |
| キャンセル済み予約 | 保持。`cancelled_at` を持つ行として残す |
| 予約座席・確定金額 | 保持。売上の根拠 |
| スタンプ | 保持。無料鑑賞券への消費後も履歴として残す |
| 入場記録 | 保持。実来場率の分析対象 |
| お知らせ・バナー | 保持。公開期間終了後は非公開として残す |
| 座席ロック | 期限切れ時に削除（一時データ） |

**削除・無効化に関する制約**

| # | 制約 |
|---|---|
| 1 | 予約が存在する上映回は削除できない |
| 2 | 未来の上映回に有効な予約（`released_at IS NULL`、6.4.2）が存在する座席は使用不可にできない。座席の物理削除は行わない |
| 3 | 会員の退会機能は実装しない。実装する場合も予約データは匿名化にとどめ、行を削除しない |

**【根拠】** 制約2を過去の上映回まで拡張した場合、
一度でも使用した座席を恒久的に無効化できなくなる。

A-04 の機能範囲は「シアター基本情報（名称／番号）の管理、座席レイアウトの閲覧、
および座席単位の使用可否切替」とする（4.8.2 / 4.8.5）。
座席の追加・削除・座標変更は行わない（システム改修として扱う。6.3.3）。
使用不可の座席は座席表で選択不可とし、残席数の集計対象から除外する（5.3-1）。

制約2はDB制約では表現できないため、A-04 側で更新前に検証する。あわせて、
決済中（`pending`）の座席は `t_reservation_seats` がまだ存在しないため
（6.4.2）、有効期限内の `t_seat_locks` も無効化禁止の対象に含める。
A-04 実装時に「ロック中または予約済みの座席は使用不可にできない」ケースを
テスト項目として追加すること。

### 6.3 シアターおよび座席

#### 6.3.1 座席テーブルの構造

表示用のラベルと配置図上の座標を分離して保持する。

| カラム | 用途 |
|---|---|
| `row_label` | 表示用の行ラベル（A, B, C...） |
| `seat_number` | 表示用の座席番号（01, 02, 03...） |
| `grid_row` | 配置図上の行位置 |
| `grid_col` | 配置図上の列位置 |
| `seat_type_id` | 座席種別 |
| `is_available` | 使用可否。使用不可の座席は座席選択画面から除外する（6.2） |

**【根拠】** 通路を挟んで「A列01〜05番」「A列06〜12番」が分かれる構成では、
06番の席は図上で7列目以降に位置する。
表示ラベルと座標を同一の値で兼ねた場合、この配置が表現できない。

**採番規則**

| 対象 | 規則 |
|---|---|
| 行ラベル | 最前列（スクリーンに最も近い列）を `A` とし、後方に向かって `B`, `C` ... |
| 27行目以降 | `AA`, `BB`, `CC` ... と同一文字を重ねる |
| 座席番号 | 各行の左端（スクリーンに向かって左）を `01` とし、2桁ゼロ埋めで連番 |
| 座席表示名 | 行ラベルと座席番号を連結する（例: `A01`, `M12`, `AA03`） |

**【根拠】** 国内の劇場で27行を超える単一ブロックは実在せず、
実際にはブロック分割（前方・中央・後方、または階層）で対応される。
本システムの最大シアターは15行であり本規則が適用される場面はないが、
座席数の拡張時に採番が破綻しないよう定義しておく。

27行目以降を `AA`, `BB` とするのは、`AB`, `AC` 形式では
`A` 行との読み違いが起きやすいためである。

**描画方針**

| # | 方針 |
|---|---|
| 1 | 通路および空きスペースには座席レコードを作成せず、座標の空きで表現する |
| 2 | 最前列のみ左右を縮小して配置し、扇形に近い客席の印象を再現する（行ごとの配置規則は6.3.3参照） |
| 3 | 描画は CSS Grid を用い、各座席に `grid-row` / `grid-column` を指定する |
| 4 | SVG は使用しない |

**【根拠】** 座席はクリック可能なボタンであり、
DOM要素の方がフォーカス管理およびイベント処理を実装しやすい。

#### 6.3.2 座席種別

すべての座席種別を「1マス = 1席」として扱う。
座席表上は装飾で区別し、予約単位および選択ロジックは一般席と同一とする。

| 種別 | 座席表での表現 | 追加料金 |
|---|---|---|
| 一般 | 標準のマス | なし |
| 車椅子 | 専用アイコン付きのマス | なし |
| エグゼクティブ | 色違い・強調表示のマス | +1,000円 |

カップルシート（2席1単位）は設けない。

**【根拠】** 「1マス=1席」の前提が崩れた場合、
座席の選択ロジック・予約単位・料金計算のすべてに例外処理が必要となる。
ペアでの利用はペア割（6.5.2）で対応する。

シーダーが行数・列数・座席種別の配置をパラメータとして受け取り、

| ２番シアター | 9行 × 12列（98席） | 2D / MOVI VIVID | 横通路あり（M相当として扱う） |
| ３番シアター | 6行 × 8列（38席） | 2D | 特集上映用の小規模スクリーン。横通路なし（XS相当） |

**座席レイアウトの基本形**

各シアターは次の構成を基本とし、規模に応じて行数・列数を調整する。

行の種類は4通り（スクリーンに近い順）。下図は各行の左右幅の関係のみを示す
模式図であり、列数・座席数は図の記号数と対応しない（正確な値は各規則の
説明文と、後述の「座席レイアウトの基本形」の表を参照）。

```
        SCREEN
 ─────────────────

  ░░[ 最前列 ]░░       ← 左右1列ずつ縮小（cols-2席）
 [ 横通路より前の中間行 ]  ← 全幅（cols席。M以上の規模のみ存在）
 · · · · · · · · · · ·  ← 横通路（M以上の規模のみ。座席は作らずgrid_rowを1つ空ける）
 [ 左ブロック ]┊[ 右ブロック ] ← 全幅のまま中央2列を通路として空けて分割（cols-2席）
 [♿♿ ── 最後列（全幅） ── ♿♿]  ← 全幅・分割なし（cols席）。両端に車椅子、
                                  L以上の規模では中央にエグゼクティブ
```

| # | 規則 |
|---|---|
| 1 | 最前列は左右1列ずつ減らす（`cols-2`席） |
| 2 | 横通路より前の中間行は全幅とする（`cols`席）。横通路はM以上の規模のみ設け、座席は作らず`grid_row`を1つ空けて表現する |
| 3 | 横通路より後方（最後列を除く）は全幅のまま中央2列を通路として空け、左右に分割する（`cols-2`席。左右の端の列は使用する）。横通路がない規模（XS・S）では最前列の次からすべてこの行になる |
| 4 | 最後列は全幅・分割なしとする（`cols`席）。横通路より前の中間行と同じ幅 |
| 5 | 最後列の両端に車椅子席2席ずつ、L以上の規模では中央にエグゼクティブ席8席を配置する |
| 6 | 通路には座席レコードを作成しない。`grid_col` / `grid_row` の空きで表現する |

XS・S 規模のシアターでは横通路を設けず、中央通路による左右分割のみとする。
XS・S・M 規模のシアターにはエグゼクティブ席を設けない（規則5、L以上のみ）。

**【根拠】** 当初「後方ほど座席数を連続的に増やし扇形とする」規則を検討したが、
中央通路の固定幅と組み合わせると行ごとに座席数を増減させる複雑なアルゴリズムが
必要になり、複雑さに見合う効果がない（デモ用の初期データであり、座席表の描画・
残席集計が破綻しないことの確認が主目的。6.3.3冒頭）。実際に縮小されるのは
最前列のみで、それ以外の行（横通路より前の中間行・分割行・最後列）はすべて
同じ全幅を占める（分割行は中央2列を通路として使わないが、左右の端の列は使用する）。

**座席種別の配置ルール**

| 座席種別 | 配置 |
|---|---|
| 車椅子 | 各シアターの最後列両端に2席ずつ |
| エグゼクティブ | L以上の規模のシアターの最後列中央に8席 |
| 一般 | 上記以外 |

### 6.4 排他制御設計

#### 6.4.1 座席ロック

`t_seat_locks` テーブルで管理する。

| カラム | 内容 |
|---|---|
| `screening_id` | 上映回 |
| `seat_id` | 座席 |
| `holder_key` | 保持者（会員はユーザーID、非会員はセッションID） |
| `expires_at` | 有効期限 |

| # | 仕様 |
|---|---|
| 1 | `(screening_id, seat_id)` にユニーク制約を設定する |
| 2 | 座席のクリック時にロックを取得し、取得できない場合は選択させない |
| 3 | 有効期限は10分 |
| 4 | 決済画面への遷移時に期限を15分へ延長する |
| 5 | 期限切れレコードはバッチ処理で削除する（10分間隔） |
| 6 | 予約確定時にロックを削除し、`t_reservation_seats` を作成する |

**【根拠】**

- アプリケーションコードのみによる排他制御では、
  わずかな時間差で複数の取得が成立する可能性が残る
- 仕様4を欠いた場合、カード情報の入力中に期限が切れ、
  決済成功後に座席を喪失する事象が発生しうる

#### 6.4.2 確定済み座席との排他

`t_reservation_seats` にはキャンセル済み・期限切れの行も残存するため、
`(screening_id, seat_id)` への単純なユニーク制約では当該座席を再販できない。

**`released_at` と生成列 `active_seat_id` を設ける。**

| カラム | 内容 |
|---|---|
| `released_at` | 座席が解放された日時。有効な予約では `NULL` |
| `active_seat_id` | 生成列。`released_at IS NULL` のとき `seat_id`、それ以外は `NULL` |

```
ユニーク制約 = (screening_id, active_seat_id)
```

MariaDB のユニークインデックスは NULL の重複を許容するため、
解放済みの行を任意件数保持しつつ、有効な予約のみを一意に制約できる。

**【根拠】** 生成列は同一行のカラムのみを参照できるため、
親テーブル `t_reservations` の `status` や `cancelled_at` を条件にできない。
解放の状態を `t_reservation_seats` 側に `released_at` として保持する必要がある。

`released_at` は、予約が `cancelled` または `expired` に遷移した時点で設定する。
更新はトランザクション内で親子を同時に行う。

`reservation_id` 経由では制約を設定できないため、
`t_reservation_seats` に `screening_id` を冗長に保持する。

**占有中とみなす状態**

| 予約の `status` | 座席の占有 | `released_at` |
|---|---|---|
| `paid` | 占有する | `NULL` |
| `cancelled` / `expired` | 占有しない | 遷移時刻 |

`t_reservation_seats` は決済完了時にのみ作成する。
`pending` の段階では `t_seat_locks` のみが座席を押さえる。

**`pending` 予約と座席ロックの対応付け**

`t_seat_locks` に `reservation_id` は持たせない。
座席選択（P-31）から決済（P-36）まで同一セッションで保持している座席ID一覧を用い、
予約確定トランザクション（8.2）の手順1として、対象ロックが
`(screening_id, seat_id, holder_key)` として現在のセッション（会員は `user:{id}`、
非会員は `session:{id}`）のものであり、`expires_at` が未経過であることを検証する。
失敗した場合はロールバックのうえ返金し、座席選択からの再実行を促す
（8.2 のユニーク制約違反時と同じ経路。「決済失敗時の扱い」表とは異なる。
あちらは課金自体が失敗した場合の扱いであり、本節は課金成立後の失敗である）。

**【根拠】** 8.2 の方針により Webhook を実装せず、決済確定は同一セッション内の
リクエストで完結するため、`holder_key` の突き合わせに追加のカラムを要しない。
`reservation_id` を `t_seat_locks` に追加する案（Webhook非実装のため復元経路が
存在せず、対価に見合わない）・`t_reservation_seats` の先行作成案（6.4.2の設計と
矛盾するため却下）も検討したが、いずれも採用しない。

`holder_key` の一致は「他人のロックを横取りしない」ための検証であり、
同一利用者の複数セッション間の競合は `(screening_id, active_seat_id)` の
一意制約が最終的に解決する。

#### 6.4.3 座席状況の反映

WebSocket は使用せず、座席表を `wire:poll` により定期再読み込みする。

| # | 仕様 |
|---|---|
| 1 | ポーリング間隔は10秒程度 |
| 2 | 選択可否の判定は必ずサーバー側のロック取得結果による |

**【根拠】** 共有レンタルサーバーでは常駐プロセスを起動できず、
WebSocketサーバーを運用できない。またポーリングでは表示に遅延が生じるため、
画面表示のみを根拠とした選択可否の判定は成立しない。

#### 6.5.3 追加料金

**上映規格の追加料金は上映編成の登録時に確定させ、購入フローでは加算しない。**

| # | 仕様 |
|---|---|
| 1 | `m_formats.default_surcharge` に規格ごとの既定額を保持する |
| 2 | 上映編成の登録時に既定額を `t_bookings.surcharge` へ自動設定する（手動上書き可） |
| 3 | 上映スケジュール表には追加料金を含んだ金額を表示する |

座席種別の追加料金（`m_seat_types.surcharge`）は座席選択時に加算する。

**【根拠】** 規格の追加料金を上映編成に確定させることで、
購入フローで規格を意識させる必要がなくなり、券種と座席の選択のみで完結する。

#### 6.5.4 計算式

```
1席あたり = 券種価格 + 上映編成の追加料金 + 座席種別の追加料金
小計       = 選択した全席の合計
支払金額   = 小計 − 割引額
```

金額はすべて円単位の整数型（`unsignedInteger`）で保持する。小数および文字列を用いない。

#### 6.5.5 金額の確定

予約成立時点の金額を `t_reservation_seats` に保存する。

**【根拠】** 表示時に価格マスタを参照した場合、
料金改定に伴い過去の予約履歴の金額が変動する。

### 8.2 Stripe

| 項目 | 内容 |
|---|---|
| モード | テストモードのみ |
| 実装方式 | Stripe Elements の自サイト埋め込み |
| カード情報の扱い | 自システムでは保持・中継しない。Stripe がトークン化した情報のみを扱う |
| Webhook | 実装しない |
| 返金 | Refund API を使用（キャンセル時） |

**【根拠】** 外部サイトへのリダイレクト方式では、
決済完了後の復帰前に離脱された場合に予約が確定しない。
Elements の埋め込みにより離脱経路を削減する。

Webhook を実装しないため、異常系では予約が `pending` のまま残置され、
期限切れで `expired` となる。テストモードでの動作としてこれを許容する。

**決済結果の検証**

クライアントから通知された決済成功をそのまま信用しない。
**サーバー側で PaymentIntent を再取得し、`status` と金額を確認したうえで**予約を確定する。

**冪等性**

決済リクエストには Idempotency Key を付与し、
通信の再送による二重決済を防止する。

**予約確定トランザクション**

決済成功後、以下を単一トランザクションで実行する。

1. 対象ロックが自分の `holder_key` のもので期限内であることを検証する（6.4.2）。失敗時はロールバックし、返金のうえ座席選択からの再実行を促す
2. `t_reservations` を `paid` に更新し、入場コードを採番する
3. `t_reservation_seats` を作成する
4. 該当する `t_seat_locks` を削除する
5. 無料鑑賞券使用時は `t_free_tickets.used_at` を設定する

手順2（`t_reservations.active_free_ticket_id`、6.1.2）または手順3
（`t_reservation_seats.active_seat_id`、6.4.2）でユニーク制約違反が発生した場合も、
手順1の失敗時と同じくロールバックし、返金のうえ座席選択からの再実行を促す。
ユニーク制約は最終防波堤であり、この経路は課金後の返金を伴う。

無料鑑賞券は追加料金や同伴者分の代金が残る場合に限り決済フローを通るため（4.5.2）、
Stripe への課金が成立した後で手順2が失敗する経路が生じうる。
`ReservationService` は課金前に対象の無料鑑賞券が未使用であることを再検証し、
決済失敗ではなく前段の入力エラーとして極力早期に弾くこと。
それでも競合した場合の最終防波堤が本制約である。

**注意（フェーズ5で置き換え予定）**: 手順5の `t_free_tickets.used_at` による管理、
および上記の未使用判定は、6.1.2 追記表「無料鑑賞券の使用状態の管理方式」の
結論により、`t_reservations.active_free_ticket_id` を単一の真実源とする方式へ
置き換える予定である。`ReservationService` 実装時は本節ではなく 6.1.2 の結論を
一次情報とすること。

**決済失敗時の扱い**

| # | 動作 |
|---|---|
| 1 | 予約を `pending` のまま保持し、座席ロックも維持する |
| 2 | 決済画面に留まり再試行を可能とする |
| 3 | ロックの有効期限（15分）経過後はロックを解放し、座席選択からの再実行とする |

## 10. バッチ処理設計

Cron により `schedule:run` を毎分実行する。

| # | 処理 | 実行間隔 | 内容 |
|---|---|---|---|
| B-01 | 座席ロックの解放 | 10分 | `expires_at` を経過した `t_seat_locks` を削除する |
| B-02 | 未決済予約の無効化 | 10分 | ロック期限を経過した `pending` の予約を `expired` に更新する |
| B-03 | スタンプ付与 | 10分 | 開始時刻を経過した上映回のうち、決済済みかつ未付与の予約にスタンプを付与する |

B-03 は `t_stamps.reservation_id` のユニーク制約により多重実行時の二重付与を防止する。

**【根拠】** これらの処理が停止した場合、
座席が解放されず販売できない状態となるため、Cronの稼働は必須要件である。

### 13.4 共通実装パターン

#### 13.4.1 館スコープの適用

顧客側では、`ResolveCinema` ミドルウェアが `{slug}` から館を解決し、
コンテナへバインドする。各コントローラおよびコンポーネントで館を再取得しない。

館非依存ページ（P-01, P-05〜P-20）には `{slug}` が無くミドルウェアを通らないため、
`App\Services\CurrentCinemaService` が明示的に解決する（4.1.3 追記表）。
これらのページ・Livewire コンポーネントで `app(Cinema::class)` を直接呼ばない。
共通レイアウトのヘッダーが先にコンテナへバインドするため通常は空のモデルが
返ることは無いが、順序に依存させず `CurrentCinemaService::resolve()` を明示的に呼ぶこと。

管理画面では、`cinema-admin` でログインしている場合に
`CinemaScope`（グローバルスコープ）が自動的に `cinema_id` の条件を付加する。

**禁止事項**

- 個別の画面に `if (auth('admin')->user()->isCinemaAdmin())` 相当の条件を記述すること
- スコープを回避する目的で `withoutGlobalScope()` を使用すること

`super-admin` による全館横断の参照は、スコープ自体を適用しない実装とする
（スコープの登録時に権限を判定する）。

#### 13.4.2 権限判定

権限判定は Policy に集約する。Blade およびコンポーネント内では
`@can` / `$this->authorize()` を用い、ロール名を直接比較しない。

```
禁止: if ($admin->role === 'super-admin')
推奨: $this->authorize('manage', Cinema::class)
```

#### 13.4.3 Livewire コンポーネントの粒度

| 用途 | 実装 |
|---|---|
| 状態を持たない表示のみ | Blade コンポーネント |
| ユーザー操作により状態が変わる | Livewire コンポーネント |
| 座席選択・上映スケジュールの日付切替・管理画面のフォーム | Livewire |
| バナー・お知らせ一覧・静的ページ | Blade |

Livewire コンポーネントは1画面1コンポーネントを基本とし、
状態を持つ子要素がある場合のみ分割する。

#### 13.4.4 バリデーション

- 管理画面のフォームは FormRequest に集約する
- Livewire コンポーネント内のバリデーションは `rules()` メソッドに定義する
- 業務ルール（上映回の重複判定、券種と座席数の一致など）は
  カスタムバリデーションルールとして実装し、コンポーネント内に直接記述しない

#### 13.4.5 金額計算

金額の算出は `PricingService` に集約する。
コンポーネント・Blade・コントローラのいずれにも計算ロジックを記述しない。

```
PricingService::calculate(Screening $screening, array $seatSelections, ?FreeTicket $ticket): PriceBreakdown
```

`PriceBreakdown` は 小計 / 割引額 / 支払金額 / 席ごとの内訳 を保持する値オブジェクトとする。

#### 13.4.6 座席ロック

ロックの取得・延長・解放は `SeatLockService` に集約する。
`t_seat_locks` テーブルへの直接操作を各所に記述しない。

```
SeatLockService::acquire(Screening $screening, Seat $seat, string $holderKey): bool
SeatLockService::extend(string $holderKey, int $minutes): void
SeatLockService::releaseAll(string $holderKey): void
SeatLockService::transfer(string $from, string $to): void
```

**未実装事項（フェーズ3/5で対応）**: 13.3 は `holder_key` を会員 `user:{id}`、非会員 `session:{id}` と
定めるが、P-33（7.8）に「会員としてログイン」「会員登録して購入」の導線があり、
ログイン成功時のセッションID再生成で `holder_key` が変わる。P-31 で取得した
ロックが所有者不明のまま最大15分残る。`transfer()` をログイン成功時・
会員登録完了時の2箇所で呼び出し、移譲元 `session:{id}` から移譲先
`user:{id}` へロックの `holder_key` を更新する。7.8 の「戻り先を保持」する
仕組みに、移譲元 `holder_key` も併せて保持する旨を追記すること。
実装はフェーズ3（認証）およびフェーズ5（予約フロー）。

#### 13.4.7 予約確定

予約確定は `ReservationService` に集約し、単一トランザクションで実行する（8.2）。
ユニーク制約違反は例外として捕捉し、返金処理を行ったうえで
座席選択画面へ誘導する。

`t_reservation_seats.seat_id` が選択中の上映回のシアターに属することは、
DB制約では表現しない（複合外部キーは割に合わない）。`ReservationService` が
確定前に検証すること。13.6 のテスト方針には無い観点のため、`ReservationService`
実装時に「他シアターの座席IDを渡すと拒否される」ケースをテスト項目として追加すること
（`SeatLockService` の並行ロック取得を検証する T-01 とは対象・観点が異なる）。

同様に、確定トランザクション内での座席ロック所有権の再検証（6.4.2、8.2手順1）も
13.6のテスト方針には無い観点のため、`ReservationService` 実装時に
「期限切れ・他人のロックでは決済確定が拒否される」ケースをテスト項目として追加すること。

**未決事項**: P-31（座席選択）〜P-36（決済）の間、「どの座席にどの券種を
割り当てたか」を保持する場所が未定義。`t_reservation_seats` は決済完了時にしか
作成されず（6.4.2）、画面をまたぐため Livewire のコンポーネント状態でも持てない。
`ReservationService` 実装時（フェーズ5）に確定させる。

### 13.6 テスト方針

網羅的なテストは作成せず、以下の観点に絞って Feature テストを作成する。

| # | テスト対象 | 検証内容 |
|---|---|---|
| T-01 | 座席の二重予約防止 | 同一座席に対する同時ロック取得で1件のみ成功すること |
| T-02 | 権限スコープ | `cinema-admin` が他館のデータを取得・更新できないこと |
| T-03 | 料金計算 | 券種・追加料金・割引・無料鑑賞券の各組み合わせで金額が一致すること |
| T-04 | キャンセル後の再販 | キャンセル済み座席が再度予約できること |
| T-05 | 上映回のバリデーション | 期間外・規格不一致・インターバル不足で登録が拒否されること |
| T-06 | スタンプ付与 | バッチの多重実行で二重付与されないこと |
| T-07 | 入場判定 | 4.6.4 の各検証条件で入場が拒否されること |
| T-08 | 予約照会 | 予約番号とメールアドレスの組み合わせが一致しない場合に参照できないこと |

セキュリティに関する検証項目（T-11 〜 T-15）は17.15に定義する。

T-01〜T-08は購入・運用フローの観点であり、シーダー（9章）はこの一覧の対象外。
シーダーは初期データの構造的な正しさ（規模ごとの構成・冪等性）を
`tests/Feature/Database/` で別途検証する。フル規模（45シアター等）を要する
検証は`DatabaseSeeder`経由のテスト1〜2件に絞り、個々のシーダーの挙動
（スケジューリングの正しさ等）は最小限の手作りフィクスチャに対して
シーダー単体を実行して検証する。全件をフル規模で毎テスト実行すると
スイート全体が著しく遅くなるため（`ScreeningSeeder`は45シアター全体で約36秒）。

**【根拠】** 金銭と排他制御に関わる箇所は、
誤りが再現しにくく発見が遅れるため、自動テストで検証する。

**実行環境**

`php artisan test` は実際の MariaDB（データベース名 `movi_testing`。開発用の `movi` とは別）に対して実行する。
生成列とユニークインデックスのNULL重複許容（6.4.2）はMariaDB固有の挙動であり、
SQLiteでは正しく検証できないため（3.5-4）。ローカルでの作成手順は README を参照。
GitHub Actions（`.github/workflows/tests.yml`）も同一の `mariadb:10.11` イメージを用いる。

未実装の `SeatLockService` を用いた T-01（同時ロック取得）を実装する際は、
`RefreshDatabase` がテストをトランザクションで包むため、複数コネクションからの
同時実行を検証できない点に注意する。`DatabaseTruncation` 等への切り替えを検討すること。

## 14. スキル定義（Claude Code）

### 14.1 スキルの種別と配置

Claude Code のカスタムスラッシュコマンドはスキルに統合されており、
`.claude/skills/{name}/SKILL.md` に配置する。
`.claude/commands/` は使用しない。

本プロジェクトでは、スキルを2種類に分けて定義する。

| 種別 | 用途 | 呼び出し | `disable-model-invocation` |
|---|---|---|---|
| **参照型** | 実装時に守るべき規約を提供する | Claude が説明文に基づき自動で読み込む | 設定しない |
| **実行型** | 明示的な指示で一連の手順を実行する | 利用者が `/{name}` で呼び出す | `true` |

**【根拠】** 実行型はコミットのように副作用を伴うため、
Claude の判断で自動的に起動されてはならない。
`disable-model-invocation: true` を設定することで、
自動読み込みを無効にし、明示的な呼び出しのみに限定する。
あわせて、使用しないスキルの説明文が文脈を消費することも防げる。

### 14.2 記述の方針

`description` には「どのような作業のときに読むか」を記述する。
本書の該当章を参照させ、内容を重複させない。

`allowed-tools` を設定し、スキルが使用できるツールを制限する。
参照型スキルには書き込み系のツールを付与しない。

### 14.3 参照型スキルの一覧

### 14.4 参照型スキルに記載する要点

#### S-01 `cinema-scope`

- 顧客側は `ResolveCinema` ミドルウェアで解決した館を使用する。再取得しない
- 管理画面は `CinemaScope` により自動で絞り込まれる
- 画面ごとに権限判定の条件式を記述しない
- `withoutGlobalScope()` を使用しない
- 館切替時は同種のページへ遷移させる

#### S-02 `admin-screen`

- 権限ごとに画面を分けない。同一画面をスコープと表示項目で切り替える
- `cinema-admin` には館セレクタを表示しない
- 権限判定は Policy に集約し、ロール名を直接比較しない
- 予約状況にメールアドレスと決済情報を表示しない
- 更新は Eloquent モデル経由で行い、一括更新（`where()->update()`）を使用しない（5.5）
- 座席の無効化（A-04）は、対象座席に有効な予約または未期限切れの `t_seat_locks` がないことを更新前に検証する（6.2 制約2）

#### S-03 `db-schema`

- 命名規則（13.2）と型の規約（13.3）に従う
- テーブル名に区分接頭辞（`m_` / `t_` / `c_`）を付し、モデルに `$table` を明示する
- `users` およびフレームワーク標準テーブルには接頭辞を付さない
- 金額は円単位の整数、区分は backed enum
- 過去データを削除しない設計とする（6.2）
- 一意制約が必要な箇所（`t_reservation_seats`, `t_seat_locks`, `t_stamps`, 各コード列）を確認する
- キャンセルを伴うテーブルでは生成列による一意制約を検討する（6.4.2）

#### S-04 `seeder`

- 冪等に実装する
- 一括挿入を使用する
- 生成規模は `SeedConfig` の定数から取得し、ロジックに直接記述しない
- 投入順序: 館 → シアター → 座席 → 映画 → 上映編成 → 上映回 → 予約
- 祇園ムビは手動データ、その他は6.3.3の固定構成で生成する
- シアター数・規模はランダムにせず定数表から取得する

#### S-05 `seat-map`

- 表示ラベル（`row_label` / `seat_number`）と座標（`grid_row` / `grid_col`）を分離する
- 通路には座席レコードを作成しない
- 使用不可の座席（`is_available = false`）は `Seat::available()` で除外し、通路と同様の空きマスとして扱う（6.2）
- 残席集計（5.3-1、7.4の○△×判定）の分母も `is_available = true` の座席のみを対象とする
- 描画は CSS Grid。SVG を使用しない
- 座席の状態を色のみで区別しない
- 全座席種別を1マス1席として扱う

#### S-06 `reservation-flow`

- ロック操作は `SeatLockService` に集約する
- 選択可否の判定は必ずサーバー側のロック取得結果による
- ロックは10分、決済画面遷移時に15分へ延長する
- 1利用者あたり1上映回・8席まで
- 予約確定は単一トランザクション。ユニーク制約違反時は返金してやり直し
- 予約確定トランザクションの手順1として、ロック所有権と期限を再検証する（6.4.2「`pending` 予約と座席ロックの対応付け」、8.2）。失敗時はロールバックのうえ返金する（ユニーク制約違反時と同じ経路。8.2「決済失敗時の扱い」表とは別）
- キャンセル時は無料鑑賞券を戻し、`released_at` を設定して座席を再販可能にする
- `released_at` は親の `status` 変更と同一トランザクションで更新する

#### S-12 `entry-gate`

- QRの内容は入場コードの文字列のみ。URLを含めない
- 入場ゲート画面は端末の所属館にスコープされる
- 判定結果は画面全体の色で表示し、3秒後に読み取り待機へ戻る
- 手入力モードで予約番号による入場処理を可能とする
- 入場の取消は `cinema-admin` も自館分を実行できる

#### S-14 `security`

- 他者のデータへの到達可否は Policy で担保する。IDの推測困難性に依存しない
- 金額の算定はサーバー側で行い、クライアントの申告値を採用しない
- 決済成功はサーバー側で PaymentIntent を再取得して検証する
- 状態を変更する操作をGETで実装しない
- `{!! !!}` を使用しない。お知らせ本文のHTMLタグは除去する
- アップロードでSVGを許可しない
- パスワード・連絡先・各種コード・APIキーをログへ出力しない

#### S-15 `screen-design`

- 画面一覧（7.1.1）のURLと画面IDに従う
- 共通レイアウト（7.2）のヘッダー・フッターを使用する
- 配色は18.2に従う。ベース白、アソートはダークブラウン、アクセントは白反転と赤系
- 状態を色のみで区別しない
- 文言は `lang/ja` に定義し `__()` 経由で参照する（20章）
- 顧客向け・管理画面を問わず丁寧語とする
- 画像は遅延読み込み。Webフォントの読み込みを必須としない

#### S-16 `seo`

- `title` は19.2の形式に従う
- `canonical` / OGP / Twitter Card を全ページに設定する
- 構造化データは館ページに `MovieTheater`、作品詳細に `Movie`
- `sitemap.xml` に上映回を含めない
- `robots.txt` で予約フロー・マイページ・予約照会・管理画面を除外する

#### S-07 `pricing`

- 計算は `PricingService` に集約する
- 上映規格の追加料金は `t_bookings.surcharge` に確定済み。購入フローで加算しない
- 割引は重複適用せず、安価な方を採用する
- 無料鑑賞券と割引は併用しない
- 予約成立時点の金額を `t_reservation_seats` に保存する
- クライアントから送られた金額を信用しない

#### S-08 `front-ui`

- モバイル基準で記述し、`md:` `lg:` で上書きする
- `sm:` `xl:` `2xl:` を使用しない
- 顧客向け画面に Flux UI を使用しない
- 上映回ボタンは折り返しで対応し、横スクロールにしない
- 画像は遅延読み込みとする
- 状態を持たない表示は Blade コンポーネント、操作を伴うものは Livewire

#### S-09 `mail`

- Brevo の SMTP リセーを使用する
- QRコードは PNG を CID 添付で埋め込み、あわせてリンクとコードのテキストを併記する
- QRコードの生成は `endroid/qr-code` の GD ライタを使用する（Imagick に依存しない）
- メールアドレス確認は無効
- 開発中の送信先を自身のアドレスに限定する

#### S-10 `batch`

- 10章の B-01 〜 B-03 を `Console/Commands` に実装する
- 多重実行に耐える実装とする（ユニーク制約または条件による除外）
- `schedule:run` の停止が機能停止に直結することを前提に、冪等性を確保する

#### S-11 `deploy-xserver`

- アセットビルドはローカルで実行し、`public/build` をアップロードする
- `storage/` を削除・上書きしない
- CLI 用 PHP のバージョンを 8.4 に揃える
- `public_html` を `public` へのシンボリックリンクとする
- `storage:link` を実行する
- Cron に `schedule:run` を毎分実行する設定を追加する

```yaml
description: コミット規約に従って変更を検証し、コミットメッセージを作成する。
argument-hint: [補足したい内容（任意）]
allowed-tools: Bash(git status:*), Bash(git diff:*), Bash(git add:*), Bash(git commit:*), Bash(git branch:*), Bash(git log:*), Read, Grep
disable-model-invocation: true
model: sonnet
---
```

## 16. 開発ルール

### 16.1 作業単位

実装は「1機能または1タスク」を単位とする。
16.2 の検証を完了するまで、次のタスクに着手しない。

**【根拠】** 複数タスクをまとめて実装した場合、
不具合の発生箇所を切り分けられず、デグレの原因特定に時間を要する。

### 16.2 タスク完了時の検証手順

各タスクの完了時に以下を順に実行する。
**いずれかが失敗した場合は修正し、V-01 から再実行する。**

| # | 手順 | 実行内容 | 判定 |
|---|---|---|---|
| V-01 | コード整形 | `vendor/bin/pint --dirty` | 差分が解消すること |
| V-02 | 静的解析 | `vendor/bin/phpstan analyse` | エラー0件 |
| V-03 | テスト実行 | `php artisan test` | 全件成功 |
| V-04 | 変更範囲の確認 | `git diff --stat` | 意図しないファイルが変更されていないこと |
| V-05 | 実装レビュー | `code-reviewer` サブエージェント（16.4） | 指摘なし、または対応済み |
| V-06 | 影響範囲の確認 | `regression-checker` サブエージェント（16.4） | 指摘なし、または対応済み |
| V-07 | 画面確認 | mb幅（375px）での表示確認 | レイアウトが破綻しないこと |

V-01 〜 V-03 は機械的に判定できるため必ず実行する。
V-05 / V-06 は判断を要する項目を対象とする。

**V-05 / V-06 で BLOCKER の指摘を受けた場合、修正のうえ V-01 から再実行する。**
WARNING は、修正するか、見送る理由を記録したうえで先へ進む。

**【根拠】** 構文エラーおよび型の不整合は静的解析で確実に検出できる。
これらをレビューの対象とすると、本来検出すべき
設計規約からの逸脱や仕様との齟齬に注意が向かなくなる。

### 16.3 導入するツール

| ツール | 用途 | 設定 |
|---|---|---|
| Laravel Pint | コード整形 | 既定の `laravel` プリセットを使用する |
| Larastan（PHPStan） | 静的解析 | レベル5から開始し、エラー0件を維持する |
| Pest または PHPUnit | テスト | 13.6 の T-01 〜 T-08 を実装する |

**【根拠】** 静的解析のレベルを最初から最大にすると、
既存コードの指摘対応に時間を要する。レベル5で開始し、
余力に応じて段階的に引き上げる。

### 16.4 レビュー用サブエージェント

#### 16.4.1 採用理由

レビューには Claude Code のサブエージェント機能を用いる。

サブエージェントは独立したコンテキストで動作し、
親セッションの実装過程を引き継がない。
実装した本人（同一コンテキスト）による見直しでは、
実装時の前提をそのまま正しいものとして扱うため、
前提自体の誤りを検出できない。

一方、サブエージェントへ渡せる情報は起動時のプロンプトのみであるため、
対象ファイルのパス、設計書の該当章、変更内容を明示的に渡す必要がある。

#### 16.4.2 定義するサブエージェント

`.claude/agents/{name}.md` として定義する。
YAML フロントマターに `name` / `description` / `tools` を記述し、
本文をシステムプロンプトとする。

| # | 名称 | 役割 | 付与するツール |
|---|---|---|---|
| A-01 | `code-reviewer` | 実装が設計書および実装規約に適合しているかを検証する | 読み取り系のみ |
| A-02 | `regression-checker` | 変更が既存機能に与える影響を検証する | 読み取り系のみ |
| A-03 | `spec-consistency` | 設計書の記述間に矛盾がないかを検証する | 読み取り系のみ |

いずれも**書き込み系のツールを付与しない。**

**【根拠】** レビュー担当が修正まで行うと、指摘内容が記録されないまま
コードが変更され、判断の妥当性を確認できなくなる。

#### 16.4.3 `code-reviewer` の検証項目

**A. 目的への適合**

差分が、指示されたタスクを過不足なく実現しているかを判定する。

| # | 検証項目 |
|---|---|
| 1 | タスクの目的が達成されているか。実装されていない要件が残っていないか |
| 2 | タスクの範囲を超えた変更が含まれていないか（依頼されていない機能、無関係なリファクタリング） |
| 3 | 将来必要になるかもしれないという理由で、現時点で使われないコードを追加していないか |
| 4 | 既存の仕組みで実現できるものを、新たに作り直していないか |
| 5 | 抽象化が過剰でないか。利用箇所が1つしかないインターフェースや基底クラスを作っていないか |

**B. ロジックの妥当性**

静的解析では検出できない誤りを判定する。

| # | 検証項目 |
|---|---|
| 6 | 条件分岐の網羅性。想定していない入力で意図しない経路に入らないか |
| 7 | 境界値の扱い（0件、1件、上限値、期限の前後、null） |
| 8 | 早期リターンと例外の使い分けが適切か。エラーを握り潰していないか |
| 9 | トランザクションの範囲が適切か。整合性を要する更新が範囲外に出ていないか |
| 10 | 日時の比較で、期限の境界（以上／超過）が仕様と一致しているか |

**C. 規約への適合**

| # | 検証項目 | 参照 |
|---|---|---|
| 11 | 館スコープの絞り込みを個別画面に記述していないか | 13.4.1 |
| 12 | 権限判定をロール名の直接比較で行っていないか | 13.4.2 |
| 13 | 金額計算を `PricingService` 以外に記述していないか | 13.4.5 |
| 14 | 座席ロックの操作を `SeatLockService` 以外に記述していないか | 13.4.6 |
| 15 | ステータス・区分を文字列リテラルで直書きしていないか | 13.3 |
| 16 | 管理操作で一括更新（`where()->update()`）を使用していないか | 5.5 |
| 17 | テーブル名の接頭辞規則および `$table` の明示 | 6.1.1 |
| 18 | Tailwind のブレークポイントが `md:` / `lg:` のみか | 13.5 |
| 19 | 顧客向け画面に Flux UI を使用していないか | 13.5 |
| 20 | 実装内容が設計書の該当章と一致しているか | 各章 |

**【根拠】** Aの観点は、実装した本人（同一コンテキスト）では判定できない。
自らが書いたコードを必要なものとして扱うため、過剰な実装を過剰と認識できない。
文脈を引き継がないサブエージェントに判定させる必要がある。

Bの観点は、静的解析とテストの双方から漏れる領域である。
本プロジェクトのテストは8件に限定しており（13.6）、
網羅的な検証を自動テストに依存できない。

#### 16.4.4 `regression-checker` の検証項目

| # | 検証項目 |
|---|---|
| 1 | 変更したモデル・サービスを参照している箇所を洗い出し、影響の有無を判定する |
| 2 | マイグレーションの変更が既存データと矛盾しないか |
| 3 | 一意制約・外部キーの追加により既存データが違反しないか |
| 4 | 既存のテストが対象範囲を網羅しているか。不足があれば追加すべきテストを指摘する |
| 5 | 削除・改名した処理の呼び出し元が残っていないか |

#### 16.4.5 起動時に渡す情報

サブエージェントは親のコンテキストを引き継がないため、
起動時に以下を明示的に渡す。

| # | 情報 |
|---|---|
| 1 | 実装したタスクの内容 |
| 2 | 変更したファイルのパス一覧（`git diff --name-only` の結果） |
| 3 | 設計書の該当章番号 |
| 4 | 実装時に判断した事項（設計書に記載のない選択をした場合） |

#### 16.4.6 出力形式

| 区分 | 意味 | 対応 |
|---|---|---|
| BLOCKER | 設計・規約に反する。または不具合を含む | 修正するまで完了としない |
| WARNING | 動作するが、規約から外れる、または保守性を損なう | 修正するか、理由を記録して見送る |
| INFO | 改善の提案 | 対応は任意 |

指摘は「該当ファイル:行番号 / 区分 / 内容 / 参照すべき章」の形式で出力する。

### 16.5 フックの利用

初期はサブエージェントを会話上で起動する運用とし、フックは導入しない。

作業が定着した段階で、V-01（Pint）を `PostToolUse` フックに、
V-02 / V-03 を `Stop` フックに移行することを検討する。

**【根拠】** フックは実行が強制されるため、
検証手順が確定する前に導入すると、
不要な実行や失敗によって作業が停止する。

### 16.6 開発環境の統一

Windows と macOS の2環境で開発するため、環境差を吸収する設定をリポジトリで管理する。

#### 16.6.1 コミット対象とする設定ファイル

| ファイル | 目的 |
|---|---|
| `.gitattributes` | 改行コードの統一 |
| `compose.yaml` | ローカルのデータベース |
| `.editorconfig` | インデント・文字コードの統一 |
| `pint.json` | コード整形ルール（既定プリセットを使う場合は不要） |
| `phpstan.neon` | 静的解析の設定 |
| `phpunit.xml` | テストの実行設定（DB接続を含む。13.6参照） |
| `.github/workflows/` | CI（GitHub Actions） |
| `.claude/` | スキル、サブエージェント |
| `docs/design.md` | 基本設計書 |
| `.env.example` | 環境変数の雛形 |
| `composer.lock` / `package-lock.json` | 依存パッケージのバージョン固定 |

`.claude/settings.local.json` は個人設定のためコミットしない。

#### 16.6.2 改行コード

`.gitattributes` により、リポジトリ内および作業ディレクトリの改行を LF に統一する。

```
* text=auto eol=lf
*.sh text eol=lf
```

**【根拠】** 設定がない場合、Windows のチェックアウトで CRLF に変換され、
macOS との間で全ファイルが差分として検出される。
またシェルスクリプトが CRLF になるとサーバー上で実行できない。

#### 16.6.3 ファイル名の大文字小文字

macOS の既定のファイルシステムは大文字小文字を区別しないが、
本番環境の Linux は区別する。

| # | 規約 |
|---|---|
| 1 | 自分で作成する Blade ファイルおよびディレクトリ名は小文字のケバブケースを用いる |
| 2 | クラスファイル名はクラス名と完全に一致させる |
| 3 | ファイル名の大文字小文字のみを変更する場合、`git mv` を使用する |

フレームワークおよびスターターキットが生成したファイルの命名は、
Laravel の規約に従い、変更しない。

**【根拠】** macOS 上で `Foo.blade.php` を `foo.blade.php` に改名しても、
Git が変更として検出しないことがある。
本番環境でのみ「ファイルが見つからない」エラーが発生する。

#### 16.6.4 環境差の吸収

| # | 規約 |
|---|---|
| 1 | パスの記述にディレクトリ区切り文字を直接書かない。`storage_path()` 等のヘルパを使う |
| 2 | `composer.lock` と `package-lock.json` を必ずコミットし、両環境で同一バージョンを使う |
| 3 | スキルに埋め込むシェルコマンドは、Windows と macOS の双方で同一に動作するものに限る |

**【根拠】** 規約3について、Windows では埋め込みコマンドが PowerShell で実行される場合がある。
`git` の基本コマンドは差異がないが、パイプや `$()` を用いた記述は環境により結果が変わる。

### 16.7 Git運用

#### 16.7.1 基本規約

| 項目 | 規則 |
|---|---|
| 常設ブランチ | `main`（統合済み） / `develop`（開発） |
| 開発の場所 | 原則として `develop` で直接作業する |
| 作業ブランチ | 大きな変更や試行錯誤を伴う作業でのみ `feature/{概要}` を `develop` から作成する |
| コミット単位 | 16.2 の検証を通過した状態で、**1つの目的につき1コミット** |
| コミットメッセージ | 16.7.2 の形式に従う |
| `main` への統合 | 実装の区切りで `develop` からマージする |

**【根拠】** 単独開発であり、並行して複数の機能を進めることがないため、
機能ごとにブランチを切る必要がない。
`main` を常に動作する状態に保ち、`develop` で作業する2本立てで足りる。

#### 16.7.2 コミットメッセージの形式

```
{type}: {変更内容の要約}

{変更の理由。1〜3行}

{補足があれば箇条書き}
```

| type | 用途 |
|---|---|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `refactor` | 挙動を変えない内部構造の変更 |
| `style` | 整形のみ |
| `test` | テストの追加・修正 |
| `docs` | ドキュメントの変更 |
| `chore` | 設定・依存パッケージ・ビルド関連 |

| # | 規約 |
|---|---|
| 1 | 要約は日本語で50文字以内 |
| 2 | 「修正」「対応」のみの、内容が判別できない表現を使わない |
| 3 | 本文は「何のために」「何を」「どう変更したか」の3点が読み取れるように書く |
| 4 | 採用した仕組みの名称を明記する（生成列、グローバルスコープ など） |
| 5 | 設計上の判断を伴う場合、基本設計書の該当章を参照する |
| 6 | AI の利用に関する記載を含めない |

**【根拠】** 規約3について、目的のみを記した本文では実装内容を辿れず、
実装内容のみを記した本文では差分を読めば分かる情報の重複となる。
双方を残すことで、後から判断の経緯と実現方法の両方を参照できる。

#### 16.7.3 コミット前の確認事項

| # | 確認 | 該当時の対応 |
|---|---|---|
| 1 | `.env`、`.htpasswd`、鍵・証明書が含まれていないか | コミットせず除外する |
| 2 | APIキー・パスワードが差分に含まれていないか | コミットせず除外する |
| 3 | `dd()` `dump()` `console.log` `debugger` が残っていないか | 削除する |
| 4 | コメントアウトされたコードが残っていないか | 削除する |
| 5 | 変更が複数の目的にまたがっていないか | コミットを分割する |
| 6 | `docs/design.md` の変更が含まれる場合、版数が1つだけ上がっているか | 複数上がっている場合、最終状態に対する1つに直す |

#### 16.7.4 `/mycommit` コマンド

上記の確認とメッセージ作成を `.claude/skills/mycommit/SKILL.md` として定義し、
`/mycommit` で実行する（14.5）。

| # | 動作 |
|---|---|
| 1 | `git status` と `git diff` の内容を取得する |
| 2 | 16.7.3 の確認を行う |
| 3 | 複数の目的にまたがる場合、分割案を提示する |
| 4 | 16.7.2 の形式でメッセージを作成する |
| 5 | 承認を得てからコミットする |

`disable-model-invocation: true` を設定し、
明示的に呼び出したときのみ実行されるようにする。
`git push` は本コマンドで実行しない。

**【根拠】** コミットは取り消しが容易でない副作用を伴うため、
AI が自律的に判断して実行する対象としない。

### 16.8 デグレ防止

| # | 規則 |
|---|---|
| 1 | テストは対象を絞らず、常に全件実行する |
| 2 | マイグレーションは既存データを破壊しない形で追加する。カラム削除は行わない |
| 3 | 共通サービス（`PricingService` / `SeatLockService` / `ReservationService`）を変更した場合、`regression-checker` を必ず起動する |
| 4 | シーダーを変更した場合、`migrate:fresh --seed` が完走することを確認する |
| 5 | 設計書を変更した場合、影響するスキルファイル（14章）の記述を確認する |

**【根拠】** 規則1について、変更箇所に関連するテストのみを実行した場合、
関連の判断自体が誤っているとデグレを検出できない。
テストは8件程度であり、全件実行の所要時間は問題にならない。

### 16.9 設計書の更新

実装中に設計書の記述と異なる判断を行った場合、
実装を完了させる前に設計書を更新する。

| # | 規則 |
|---|---|
| 1 | 設計書が実装より古い状態を残さない |
| 2 | 未確定事項（★）を解決した場合、12章の一覧からも削除する |
| 3 | 変更が実装規約（13章）に及ぶ場合、該当するスキルファイルも更新する |
| 4 | 版数を上げるのはコミット直前とし、1コミットにつき最大1つとする。同一コミット内で複数回編集した場合も、最終状態に対して1つだけ採番する |
| 5 | 実装中に判明した残課題は12章に区分「実装」として記載し、解決したコミットで削除する |

**【根拠】** 設計書とコードが乖離した状態では、
スキルファイルおよびサブエージェントによるレビューが誤った基準で行われる。

**【根拠】** 規則4について、版数は git のリビジョンを参照するラベルである。
1コミット内で複数上がると、中間の版に対応するコミットが存在せず、
その状態を取り出せない。

### 16.10 モデルの使い分け

作業の性質に応じて使用するモデルを切り替える。
思考を要する作業には上位モデルを、定型的な作業には下位モデルを割り当てる。

**【根拠】** ファイル検索・整形・雛形生成のような機械的な作業は、
下位モデルでも上位モデルと同等の結果が得られる。
全作業を上位モデルで実行すると、利用枠を定型作業で消費し、
設計判断を要する場面で残量が不足する。

#### 16.10.1 作業区分とモデル

| 区分 | 作業 | モデル |
|---|---|---|
| 上位 | 排他制御・料金計算・予約確定トランザクション・権限スコープの設計と実装 | `fable` / `opus` |
| 上位 | デグレの原因調査、想定外の挙動の切り分け | `fable` / `opus` |
| 上位 | 設計書の変更、章間の整合性確認 | `fable` / `opus` |
| 中位 | 通常の機能実装（管理画面のCRUD、Livewireコンポーネント、フォーム） | `sonnet` |
| 中位 | テストコードの作成 | `sonnet` |
| 上位 | 実装レビュー、影響範囲の確認 | `opus` |
| 下位 | Blade / Tailwind のマークアップ | `haiku` |
| 下位 | シーダーのデータ定義、マイグレーションの雛形生成 | `haiku` |
| 下位 | 命名の一括変更、整形、文言修正 | `haiku` |
| 下位 | ファイル検索、既存コードの所在確認 | `haiku` |

長時間にわたり文脈を保持する必要がある作業（設計全体の見直し、
複数機能をまたぐリファクタリング）では `fable` を用いる。

#### 16.10.2 メインセッションでの切り替え

**既定は `opus` とする。** 作業に着手する前に `/model` で切り替える。

| 作業 | 操作 |
|---|---|
| 設計判断を伴う実装、調査、設計書の変更 | 既定のまま（`opus`） |
| 長時間にわたり文脈を保持する作業 | `fable` へ引き上げる |
| 定型実装、テストコード | `sonnet` へ引き下げる |
| マークアップ、データ定義、一括置換、ファイル検索 | `haiku` へ引き下げる |

**【根拠】** 切り替えを忘れた場合の影響を比較すると、
上位モデルで定型作業を実行した場合は利用枠を余分に消費するにとどまるが、
下位モデルで設計判断を伴う実装を実行した場合は
規約からの逸脱や排他制御の誤りが混入し、後工程で修正コストが発生する。

前者は費用の問題であり、後者は品質の問題である。
既定は品質側に倒す。

#### 16.10.3 サブエージェントへの割当

サブエージェント定義の `model` フロントマターで指定する。
指定できる値は `sonnet` / `opus` / `haiku` / `fable`、
完全なモデルID（例: `claude-opus-5`）、または `inherit`。
省略した場合は `inherit` となり、メインセッションと同じモデルが使われる。

| サブエージェント | モデル | 理由 |
|---|---|---|
| `code-reviewer` | `opus` | 設計書との照合に判断を要する |
| `regression-checker` | `opus` | 影響範囲の推定に判断を要する |
| `spec-consistency` | `opus` | 章をまたぐ整合性の検証に文脈の保持を要する |

レビューは実装の誤りを検出する最後の工程であるため、いずれも下位モデルへ引き下げない。

```yaml
---
name: code-reviewer
description: 実装完了時に、設計書および実装規約への適合を検証する。修正は行わない。
tools: Read, Grep, Glob
model: opus
---
```

**注意**: 環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` が設定されている場合、
フロントマターの `model` より優先される。
本プロジェクトでは設定しない。

#### 16.10.4 適用しない場面

以下では下位モデルへの切り替えを行わない。

| # | 場面 | 理由 |
|---|---|---|
| 1 | 金銭に関わる処理（料金計算、決済、返金） | 誤りが直接的な損害となる |
| 2 | 排他制御（座席ロック、ユニーク制約） | 誤りが再現しにくく、発見が遅れる |
| 3 | 権限判定 | 誤りが情報漏洩につながる |
| 4 | 原因が特定できていない不具合の調査 | 調査対象の絞り込み自体に判断を要する |

## 17. セキュリティ設計

本システムは、決済情報・個人情報・座席在庫を扱う。
以下に脅威と対策を定義する。

### 17.1 認証

#### 17.1.1 顧客認証

| # | 要件 |
|---|---|
| 1 | ログインIDはメールアドレス。認証はスターターキットの標準実装を使用する |
| 2 | パスワードは8文字以上とし、ハッシュ化して保持する（Laravel標準の bcrypt） |
| 3 | ログイン試行にレート制限を設ける（同一IPおよび同一メールアドレスに対し1分あたり5回） |
| 4 | ログイン成功時にセッションIDを再生成する（セッション固定攻撃の防止） |
| 5 | メールアドレス確認は無効とする（8.3）。この判断はスパム登録を許容する前提に立つ |

#### 17.1.2 管理者認証

| # | 要件 |
|---|---|
| 1 | 顧客とは別の `admin` ガードを使用し、セッションを分離する |
| 2 | ログインIDは発行された文字列ID。メールアドレスを使用しない |
| 3 | パスワードは12文字以上とし、`super-admin` が発行・再設定する |
| 4 | ログイン試行にレート制限を設ける（1分あたり5回） |
| 5 | メールを起点とする認証導線（招待、リセットリンク）を持たない |
| 6 | 無効化された管理者はログインできない |

**【根拠】** 管理者アカウントはメールによる復旧手段を持たないため、
パスワードの強度要件を顧客より高く設定する。

#### 17.1.3 設置端末の権限

入場ゲート端末は常時ログインした状態で館内に設置される。
`gate` ロール（4.8）を用い、入場確認以外の操作を行えないようにする。

| # | 要件 |
|---|---|
| 1 | ゲート端末には `gate` ロールのアカウントを使用する |
| 2 | `cinema-admin` および `super-admin` のアカウントを設置端末に常時ログインさせない |
| 3 | 端末はキオスクモードで起動し、他のURLへ遷移できないようにする（運用要件） |

### 17.2 認可

#### 17.2.1 基本方針

**他者のデータへの到達可否は、識別子の推測困難性ではなく認可で担保する。**

| # | 要件 |
|---|---|
| 1 | 予約の参照・キャンセルは、所有者（会員本人）または非会員の照合成功を条件とする |
| 2 | URLに含まれるIDを変更して他者のデータへ到達できないことを Policy で保証する |
| 3 | `cinema-admin` および `gate` は所属館のデータのみを取得できる |
| 4 | 絞り込みはグローバルスコープで一元管理し、個別画面に条件を記述しない |
| 5 | `withoutGlobalScope()` を使用しない |

**【根拠】** 予約詳細のように連番IDでアクセスできる画面では、
IDを変更するだけで他者の予約を参照できる状態になりやすい（IDOR）。
Policy による所有者チェックを必須とする。

#### 17.2.2 予約照会のレート制限

予約照会画面（4.3.5）の方式Bは、メールアドレス・電話番号・上映日の3項目で照会する。
総当たりによる探索を防ぐため、レート制限を設ける。

| 対象 | 制限 |
|---|---|
| 予約照会（方式A・B共通） | 同一IPに対し1分あたり5回、1時間あたり20回 |
| 入場コードによる照会 | 同一IPに対し1分あたり10回 |

上限に達した場合は一定時間の待機を求め、失敗理由を詳細に返さない。

### 17.3 決済

| # | 要件 |
|---|---|
| 1 | クレジットカード情報を自システムで保持・中継しない。Stripe Elements によりブラウザから Stripe へ直接送信する |
| 2 | 金額の算定・割引判定・無料鑑賞券の適用はサーバー側で行い、クライアントからの申告値を採用しない |
| 3 | 決済成功はクライアントの通知を信用せず、サーバー側で PaymentIntent を再取得して `status` と金額を検証する |
| 4 | 決済リクエストに Idempotency Key を付与し、再送による二重決済を防止する |
| 5 | 返金は予約1件につき1回のみ実行できるものとし、二重返金を防止する |
| 6 | Stripe のシークレットキーを `.env` に保持し、コードおよびリポジトリに含めない |

**【根拠】** 要件1により、カード情報が自システムを通過しない。
要件2を欠いた場合、リクエストの改ざんにより任意の金額で決済できる。

### 17.4 個人情報の取り扱い

#### 17.4.1 保持する情報

| 情報 | 対象 | 保持理由 |
|---|---|---|
| フリガナ（カタカナ） | 会員・非会員 | 本人照合、窓口での呼び出し |
| メールアドレス | 会員・非会員 | 予約確定通知、本人照合 |
| 電話番号 | 会員・非会員 | 本人照合、窓口での照会（会員登録の必須項目、7.15） |
| 予約履歴・入場記録 | 会員・非会員 | スタンプの根拠、実績分析 |

クレジットカード情報および住所は保持しない。

#### 17.4.2 表示範囲の制限

| 画面 | 表示する | 表示しない |
|---|---|---|
| 管理画面の予約状況 | 予約者名、座席、券種、入場状態 | メールアドレス、電話番号、決済情報 |
| 管理画面の予約検索 | 予約番号、予約者名、作品、上映日時、座席、入場状態 | メールアドレス、電話番号、決済情報 |
| 入場ゲート | 作品、上映時刻、シアター、座席、枚数 | 連絡先、決済情報 |

**【根拠】** 劇場スタッフが日常業務で顧客の連絡先を参照する必要がない。
参照できる状態を作らないことで、持ち出しの経路を断つ。

#### 17.4.3 ログへの出力禁止

以下をアプリケーションログおよび例外レポートに出力しない。

| 対象 |
|---|
| パスワード、パスワードハッシュ |
| メールアドレス、電話番号 |
| 入場コード、無料鑑賞券コード |
| Stripe のシークレットキー、PaymentIntent の秘匿情報 |
| TMDB / Brevo / Turnstile の各キー |

`config/logging.php` の設定および例外ハンドラで、
上記を含むリクエストパラメータをマスクする。

**【根拠】** 例外発生時にリクエスト全体がログへ出力される実装では、
決済フォームの入力内容がそのまま残る。

#### 17.4.4 データの削除

会員の退会機能は実装しない（2.5）。
実装する場合も、予約データは氏名・連絡先を匿名化するにとどめ、行を削除しない。

### 17.5 入力値の検証と出力

#### 17.5.1 入力

| # | 要件 |
|---|---|
| 1 | すべての入力を FormRequest またはコンポーネントの `rules()` で検証する |
| 2 | 検索・並び替えのパラメータをそのままクエリに渡さない。許可値のリストと照合する |
| 3 | `DB::raw()` に外部入力を渡さない |
| 4 | 氏名は全角カタカナ、電話番号は半角数字に制限する |
| 5 | 予約番号・入場コードは形式を検証したうえで照会する |

#### 17.5.2 出力

| # | 要件 |
|---|---|
| 1 | Blade の `{{ }}` によるエスケープを使用する。`{!! !!}` を使用しない |
| 2 | お知らせ本文は Markdown として保持し、レンダリング時にHTMLタグを除去する（4.7.1） |
| 3 | 外部サイトへのリンクに `rel="noopener noreferrer"` を付与する |
| 4 | バナーのリンクURLはスキームを `http` / `https` に限定する |

**【根拠】** 要件4を欠いた場合、`javascript:` スキームを登録することで
スクリプトを実行できる。

#### 17.5.3 CSRF

| # | 要件 |
|---|---|
| 1 | 状態を変更する操作はすべて POST / PUT / DELETE で行う |
| 2 | GETリクエストで状態を変更しない（入場処理、キャンセル、精算のいずれも） |
| 3 | Laravel の CSRF トークン検証を無効化しない |

**【根拠】** 入場処理をGETで実装した場合、
URLの再読み込みやブラウザの先読みによって意図しない入場が記録される。

### 17.6 ファイルアップロード

対象はバナー画像のみ（4.7.3）。

| # | 要件 |
|---|---|
| 1 | 拡張子とMIMEタイプの双方を検証する |
| 2 | 許可する形式は jpg / png / webp / avif のみ。**SVGを許可しない** |
| 3 | ファイル名はアプリケーション側で採番し、アップロード時の名称を使用しない |
| 4 | 保存先は `storage/app/public` とし、公開ディレクトリへ直接書き込まない |
| 5 | 上限サイズは2MB |
| 6 | アップロード操作は `super-admin` に限定する |

**【根拠】** SVGはXMLであり、スクリプトを含めることができる。
画像として表示した際にスクリプトが実行される経路が生じるため許可しない。

### 17.7 通信とHTTPヘッダ

| # | 要件 |
|---|---|
| 1 | 全ページをHTTPSで提供する。HTTPへのアクセスはリダイレクトする |
| 2 | セッションCookieに `Secure` / `HttpOnly` / `SameSite=Lax` を設定する |
| 3 | `X-Content-Type-Options: nosniff` を付与する |
| 4 | `Referrer-Policy: strict-origin-when-cross-origin` を付与する |
| 5 | `X-Frame-Options: SAMEORIGIN` を付与する |
| 6 | HSTS を有効にする |

**Content-Security-Policy**

CSP を導入する。段階的に強度を上げる方針とする。

**第1段階（必須）**

```
default-src 'self';
script-src 'self' 'unsafe-eval' https://js.stripe.com https://challenges.cloudflare.com;
style-src 'self' 'unsafe-inline';
img-src 'self' data: https://image.tmdb.org;
font-src 'self';
connect-src 'self' https://api.stripe.com;
frame-src https://js.stripe.com https://challenges.cloudflare.com https://www.google.com;
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'self';
```

| ディレクティブ | 判断 |
|---|---|
| `script-src` の `'unsafe-inline'` | **許可しない。** XSS の主要な経路であり、最優先で塞ぐ |
| `script-src` の `'unsafe-eval'` | 第1段階では許可する。Alpine.js が HTML 属性内の式を `Function` 構文で評価するため |
| `style-src` の `'unsafe-inline'` | 許可する。`x-show` 等が `style` 属性を直接書き込むため。`script-src` と比較してリスクは限定的 |
| `object-src 'none'` | プラグインの読み込みを禁止する |
| `frame-ancestors 'self'` | クリックジャッキングを防止する |

**第2段階（全機能の実装完了後に着手する）**

`config/livewire.php` の `csp_safe` を有効にし、`'unsafe-eval'` を除去する。
有効化すると Alpine も CSP 対応の評価器を使用するため、
インライン式が使えなくなり、ロジックを `Alpine.data()` のコンポーネントへ
切り出す必要が生じる。

座席選択画面など式が複雑になる箇所で書き換えが発生しうるため、
**機能の実装が完了してから着手する。**
共通レイアウトのヘッダー（`components/front/header.blade.php` の劇場切替 `x-on:change`）も
書き換え対象に含まれる。

**【根拠】** `'unsafe-inline'` を許可した CSP は、XSS に対してほぼ機能しない。
一方 `'unsafe-eval'` は、攻撃者が任意の文字列をスクリプトとして注入できる状態が
別途成立していなければ悪用できない。両者の優先度は等しくない。

### 17.8 座席在庫の保護

| # | 要件 |
|---|---|
| 1 | 座席の二重予約をDBのユニーク制約で防止する（6.4.2） |
| 2 | 1利用者が保持できるロックを1上映回・8席までに制限する（4.3.4） |
| 3 | ロックの有効期限を設け、期限切れをバッチで解放する（10章） |
| 4 | ロックの保持者を `holder_key` で識別し、他者のロックを解放できないようにする |

**【根拠】** 座席の買い占めは金銭的な被害を伴わないが、
販売機会の損失として営業を妨害しうる。
アプリケーションの制限とDBの制約の双方で防ぐ。

### 17.9 秘匿情報の管理

| # | 要件 |
|---|---|
| 1 | APIキー・シークレットは `.env` に保持し、コードに記述しない |
| 2 | `.env` をリポジトリに含めない |
| 3 | `.env` が公開ディレクトリから参照できない配置とする（`public_html` はシンボリックリンク） |
| 4 | 本番環境で `APP_DEBUG=false` とする |
| 5 | `php artisan config:cache` により設定値をキャッシュする |

**【根拠】** 要件4を欠いた場合、例外画面に環境変数の内容が表示される。

### 17.10 公開範囲の制限

本サイトは公開ネットワーク上に配置するが、
**サイト全体に Basic 認証を設定し、閲覧者を限定する。**

| # | 要件 |
|---|---|
| 1 | `.htaccess` によりサイト全体へ Basic 認証を適用する |
| 2 | 認証情報は応募書類等で個別に案内し、リポジトリに記載しない |
| 3 | パスワードファイル（`.htpasswd`）は公開ディレクトリの外に配置する |
| 4 | 管理画面（`/admin`）は Basic 認証に加え、アプリケーションの認証を要する |

**副次的な影響**

| 項目 | 影響 |
|---|---|
| SEO | 検索エンジンがクロールできないため、19章の施策は検索結果に反映されない |
| OGP | SNS でのリンクプレビューが生成されない |
| 外部サービスからのコールバック | Stripe の Webhook を使用しないため影響しない |

**【根拠】** 本サイトはデモンストレーションを目的とし、不特定多数の利用を想定しない。
また管理画面のデモ用アカウントを案内する必要があるため、
アプリケーション認証のみでは保護として不十分である。

### 17.11 リポジトリの公開

ソースコードは公開リポジトリで管理する。

| # | 要件 |
|---|---|
| 1 | `.env` をコミットしない。`.gitignore` に含まれていることを初回コミット前に確認する |
| 2 | 認証情報・APIキー・Basic 認証のパスワードを README およびコードに記載しない |
| 3 | `.htpasswd`、SSH鍵、証明書をコミットしない |
| 4 | `storage/app/public` 配下のアップロード画像をコミットしない |
| 5 | 設計書（本書）はリポジトリに含める。ただしサーバー識別情報を記載しない |

**【根拠】** 要件1について、一度コミットした情報は削除してもコミット履歴に残る。

所有ドメインからの迷惑メール送信に悪用されうる。
Stripe のキーは GitHub のシークレット検出により自動的に無効化される。

## 18. デザイン方針

### 18.1 コンセプト

古典的な映画館建築の重厚さを基調とし、白を基調とした現代的な明るさと組み合わせる。
参照するイメージは、装飾的な内装を持つ1920年代の劇場建築である。

館ごとの性格（4.1.1）は配色を変えるのではなく、
写真・文章・掲載する作品の傾向で表現する。
チェーン全体で統一された印象を保つ。

### 18.2 配色

| 役割 | 色 | 用途 |
|---|---|---|
| ベース | 白（`#FFFFFF`） | 背景、コンテンツ領域 |
| アソート | ダークブラウン | ヘッダー、フッター、セクション見出しの背景 |
| アクセント | 白（ダークブラウン上での反転） | ダークブラウン背景上のテキスト、ボタン |
| アクセント | 赤系 | 重要なお知らせ、購入ボタン、満席表示 |
| 補助 | グレー階調 | 罫線、非活性状態、補足テキスト |

**【根拠】** ベースを白とすることで上映スケジュール表の可読性を確保する。
情報量の多い画面で背景を暗くすると、長時間の閲覧に耐えない。

**座席表の配色**

| 状態 | 配色 |
|---|---|
| 選択可 | 淡いブルー |
| 選択中 | 濃いブルー（枠線を強調） |
| 予約済み・ロック中 | グレー |
| 車椅子席 | グレー＋専用アイコン |
| エグゼクティブ席 | 別色＋`EXE` の表記 |

座席の状態を色のみで区別せず、枠線・アイコン・記号を併用する（5.2）。

### 18.3 タイポグラフィ

| 用途 | 方針 |
|---|---|
| 本文 | システムフォントを基本とする。Web フォントの読み込みを必須としない |
| 見出し | 本文と同系統のフォントで、太さとサイズで階層を表現する |
| 数字（上映時刻・料金・座席番号） | 等幅の数字を使用し、桁の揃いを確保する |

**【根拠】** Web フォントの読み込みは初期表示を遅らせる。
上映スケジュールの確認が主目的であるため、表示速度を優先する。

### 18.4 レイアウト

| # | 方針 |
|---|---|
| 1 | コンテンツ幅の上限を設け、大画面での間延びを防ぐ |
| 2 | セクションの区切りをダークブラウンの帯で表現する |
| 3 | 角丸を過度に用いず、直線的な構成とする |
| 4 | 影を多用しない。階層は罫線と余白で表現する |

## 19. SEO

### 19.1 方針

館ごとのページが検索結果に表示されることを目的とする。
複雑な施策は行わず、基本的な項目を確実に実装する。

**前提**: 本サイトは Basic 認証により閲覧を制限するため（17.10）、
実際には検索エンジンにインデックスされない。
本章の施策は、認証を解除した場合に機能する状態を作ることを目的とする。

### 19.2 メタ情報

各ページに `title` と `meta description` を設定する。

| ページ | title の形式 |
|---|---|
| チェーントップ | `MOVI｜映画館・上映スケジュール` |
| 館トップ | `{館名}｜MOVI` |
| 上映スケジュール | `上映スケジュール｜{館名}｜MOVI` |
| 作品詳細 | `{作品名}｜{館名}｜MOVI` |
| お知らせ詳細 | `{記事タイトル}｜お知らせ｜{館名}｜MOVI` |
| 静的ページ | `{ページ名}｜MOVI` |

`meta description` は各ページの内容を要約した120文字程度とする。
館ごとのページでは館名と所在地を含める。

### 19.3 実装項目

| # | 項目 | 内容 |
|---|---|---|
| 1 | 正規URL | `<link rel="canonical">` を全ページに設定する |
| 2 | OGP | `og:title` / `og:description` / `og:image` / `og:type` / `og:url` を設定する。画像は作品のポスターまたはサイト共通の画像 |
| 3 | Twitter Card | `summary_large_image` を設定する |
| 4 | 構造化データ | 館ページに `MovieTheater`、作品詳細に `Movie` を JSON-LD で記述する |
| 5 | `sitemap.xml` | 館ページ・作品詳細・お知らせ・静的ページを含める。上映回は含めない |
| 6 | `robots.txt` | 予約フロー（`/screenings/*`）、マイページ、予約照会、管理画面をクロール対象外とする |
| 7 | 見出し構造 | `h1` を各ページに1つ置き、階層を飛ばさない |
| 8 | 画像 | 意味のある画像に `alt` を設定する |
| 9 | 内部リンク | パンくずリストを館配下のページに設置し、`BreadcrumbList` の構造化データを付与する |

**【根拠】** 項目6について、予約フローの各画面は上映回IDに依存するため
時間の経過とともに存在しなくなる。クロール対象に含めると404が蓄積する。

### 19.4 実装しない項目

| 項目 | 理由 |
|---|---|
| AMP | 対象外 |
| 動的レンダリング | サーバーサイドレンダリングのため不要 |
| 多言語向けの `hreflang` | 単一言語のため |

## 20. 文言と多言語化

### 20.1 方針

表示文言を Blade に直接記述せず、言語ファイルに定義して参照する。

| # | 規約 |
|---|---|
| 1 | アプリケーションのロケールは `ja` 固定とする |
| 2 | フォールバックロケールを `en` とする |
| 3 | 画面の文言は `lang/ja/*.php` に定義し、`__()` を経由して参照する |
| 4 | ブラウザの言語設定による自動切り替えは行わない |
| 5 | 言語切替のUIを設けない |

**【根拠】** 文言を Blade に直接記述すると、
表記の修正時に該当箇所をすべて探す必要が生じる。
言語ファイルへの分離は多言語化の準備であると同時に、
文言の一元管理という実利がある。

ブラウザの言語設定で切り替える構成は、
サイト本文が日本語のみである以上、
バリデーションメッセージだけが英語で表示される不整合を生む。

### 20.2 バリデーションメッセージ

`lang/ja/validation.php` を配置し、日本語で表示する。
属性名は `attributes` に定義し、「氏名は必須です」のように項目名を日本語で表示する。

### 20.3 文言のトーン

| # | 規約 |
|---|---|
| 1 | 顧客向け・管理画面を問わず丁寧語とする |
| 2 | エラーの原因を利用者の過失として表現しない |
| 3 | 操作を促す文言は、次に何をすべきかを明示する |
| 4 | 専門用語を顧客向け画面で使用しない（「トランザクション」「ロック」など） |
